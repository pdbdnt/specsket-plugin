# Specsket product ingestion

Use this skill only for the `product_ingestion` workflow and `product` entity.

Read [the workflow contract](../../references/workflow-contract.md), [the field catalog contract](../../references/field-catalog-contract.md), [the evidence contract](../../references/evidence-contract.md), and [the ingestion preview contract](../../references/ingestion-preview-contract.md) before calling write tools.

For a supplied product, family, collection, category, or catalogue URL, follow the workflow contract's visible source review before and during extraction: open the supplied page in the in-app browser by default, select desktop site or desktop viewport mode and the largest practical panel when those controls exist, show each exact official product page as it is checked, and leave the most relevant product page open for the user. Do not use mobile mode or device emulation unless the user requests mobile verification or desktop presentation is unavailable. Structured extraction may run alongside the visible pass; browser visibility does not replace exact field evidence.

Analyze attached client files before making product-specific MCP calls. Follow [the client analysis contract](../../references/client-analysis-contract.md), create resumable family checkpoints for large batches, and keep every value evidence-bound. A local path alone does not make files available to ChatGPT; inspect only files the host actually exposes.

When the user supplies an official product, family, collection, category, or catalogue URL, declare the selection scope before extraction. Use `parent_product` by default for collection/category requests; use `orderable_source_identity` only for an explicit exact-item request and `category_occurrence` only for a per-category request. Represent a finite selection as `cap_mode: bounded` with a positive product-selection cap, or use `cap_mode: all_discovered` without a product cap. Keep crawl/page/byte/evidence/cost budgets separate: exhausting an operational budget makes discovery unresolved and requires continuation or scope revision. Every selected parent retains all documented in-scope orderable identities. Representative sampling is allowed only when explicitly requested as `exact_identity_subset` and must remain labeled partial. Inventory the supplied page first, then follow relevant manufacturer-controlled links and official documents. Never create variants by multiplying independent option lists.

Expand manufacturer-controlled certification accordions, download modals, tabs, selector panels, and other interactive certification surfaces that are visible on the official page. Record every literal certification label, including repeated labels, before normalizing references. For configurable products, compare certification results across every distinct selector state represented by documented combinations. Reuse one coverage state only after the official UI proves those selector states expose the same certification set; do not multiply a collection-level certificate across SKUs or imply SKU applicability merely because it appears on the collection page.

After the initial source inventory and before claiming a complete field preview, call `specsket_get_capabilities`. If that tool or the **Specsket MCP Tools Beta** connection is unavailable, stop the live staging phase and explain that the public plugin supplies instructions but live Specsket access requires a separate Streamable HTTP MCP connection to `https://integrations.specsket.com/mcp`, followed by Specsket OAuth and a new chat. Do not infer the user's identity, permissions, destination, schemas, or live Specsket state, and do not claim that the current-schema preview was completed, anything was validated, or anything was staged.

Require `product_ingestion.validate` before normalizing and `product_ingestion.stage` before offering to stage. Fetch the `current` product schema through `specsket_get_entity_schema`; when product presentation is advertised, set `include_product_presentation_contracts` to true. Never hard-code a schema version, wrapper shape, or field IDs from UI labels or old examples.

The research contract's `field_catalog` is the live human-readable Product Wizard hierarchy. Use it to explain and organize fields, but never submit it as the entity schema or presentation envelope. If the user asks for all available fields during ingestion, show the complete active catalog grouped by tab and section and keep compatibility, presentation, and contextual dynamic descriptors separate.

After bounded discovery and schema retrieval, render the complete pre-validation preview required by the ingestion preview contract. Use the live field catalog for friendly tab and section organization, include every returned current-schema field, and show literal detected values or counts, proposed mappings, evidence/status, scope, and next action. Make image and document URLs clickable and preserve document availability separately from applicability. Complete this preview before offering the immutable topology choice or a final validation summary.

Build the live `product-source-coverage@1` sidecar before topology or validation. Inventory every exact official product-detail URL; selector axes and literal option pools; documented, inspected, and unresolved selector states; typed source variant identities; resolved article/SKU identifiers when published; document occurrences; certification files, unlinked references, test/compliance claims, and manufacturer certifications; gated or request-only availability; and conflicts. Reconcile each detected count to occurrence entries. For configurable records, every inspected state must carry either an exact manufacturer identity or a canonical manufacturer-controlled variant URL identity. Preserve the manufacturer's literal identity type—SKU, Item Number, Article Number, Product Code, Catalogue Number, Order Number, Reference Number, or canonical variant URL—and reconcile those identities one-to-one with enabled presentation combinations. Never copy a URL slug or numeric suffix into a manufacturer SKU merely because it is unique. When only a canonical URL proves identity, use the contract's deterministic internal `SRC-…` SKU with `sku_origin: generated_from_source_identity`, retain the URL as `source_identity`, and leave manufacturer SKU evidence absent. Use the presentation option `external_key` values as the corresponding coverage selection keys and preserve literal option labels so each identity also matches its exact enabled tuple. `complete` means the official-source search was fully accounted, not that every referenced file was obtainable. A complete manifest may retain request-only documents, but it cannot retain unresolved selector states. Pass the exact same complete sidecar through validation and staging so the signed receipt binds it.

When capabilities enable `product_discovery_scope_contract`, this paragraph supersedes the legacy coverage `@1` procedure above. Upload the immutable batch-wide discovery manifest in bounded fragments, finalize its canonical digest, then create an ingestion execution whose partitions may span several validation chunks or jobs. Every partition and chunk-local `product-source-coverage@2` sidecar binds the same scope digest and execution partition digest. Inventory every discovered source parent and category occurrence; every documented orderable identity; selected, excluded, and unresolved dispositions; output-parent split lineage; official evidence; and global counts. Preserve the manufacturer's literal identity type. An exact manufacturer-SKU request filters strictly to `manufacturer_sku`; other exact-item requests may use any official orderable identity. Never relabel another identifier or canonical URL as a manufacturer SKU. A generated `SRC-...` value is internal only. Pass only records in the current validation/staging chunk through coverage `@2`; do not duplicate the complete batch manifest in every chunk. Omitted or duplicated identities across output records, chunks, or jobs block execution completion. Scope-less or coverage `@1` history is `Legacy scope unverified` and cannot claim parent completeness.

When the product page lacks an orderable matrix, inspect prominent official datasheets, schedules, order guides, specifications, and catalogues before concluding that identifiers are unavailable. Extract tables row by row, carry merged or grouped headers into each row, and bind the official identifier to the exact documented edge, size, thickness, color/finish, performance, and packaging tuple. Manufacturer-labeled Item Numbers and equivalent order identifiers may serve as variant SKUs while retaining their original identity kind and PDF page/table evidence. Do not invent rows or multiply independent option pools.

The preview's certification accounting is a completion gate. Show literal detected, normalized, excluded, and unresolved counts and names, with each encountered label assigned to exactly one outcome. Preserve duplicate labels as separate detected occurrences until their evidence and modal behavior prove they are the same reference. A certification with no file URL remains visible as a source-page reference with its actual availability state and bounded next action; never fabricate a download URL. Manufacturer or corporate certifications must retain manufacturer-level applicability instead of being promoted to product, family, selector, combination, or SKU evidence. On a configurable record, every normalized product-specific certification must set `applicability_occurrence_id` to its normalized combination-scoped Download applicability occurrence; that occurrence must retain the exact combination IDs and SKU aliases.

Only after the preview completion gate passes, show the recommended product structure, resulting product-record count, documented combination counts, unsupported orderable axes, and unresolved source nodes. Let the user keep the recommendation or explicitly choose separate product records. Treat that pre-staging choice as immutable for the job; changing it requires rebuilding the presentation envelope, revalidation, a refreshed preview for affected fields, and a new confirmation summary.

In every shortlist, selected-product list, topology recommendation, and final pre-validation summary, start with `Recommended scope: N products` and display each product name as a clickable exact official product-detail URL. Include manufacturer, recommendation reason, proposed structure/count, coverage status, and unresolved source nodes. Do not substitute a collection/search URL for an available product-detail URL or leave the exact link only inside a checkpoint or field table.

When capabilities advertise `analysis_location: client`, do not call specification-analysis start, poll, or assessment tools. ChatGPT owns file inspection, cross-file product linking, family grouping, dynamic profile creation, and evidence mapping. Infer which properties are relevant to the family, but never infer an unsupported property value. Preserve `not_found`, `insufficient_evidence`, `conflicting_evidence`, `not_applicable`, and `requires_vendor_confirmation` explicitly.

Group only genuinely equivalent product contexts. Submit each family profile once in the request-level `product_profile_catalog`; each record references its `technical.profile_key` and carries record-specific observations, trace, metadata, and evidence. Use only the live schema's generated submission contract and limits.

When the current schema is `product@3`, include every profile property's explicit record state, value origin, value, unit, test/classification system, scope, and nested evidence references. The outer field evidence must be the exact union of all nested references, including every conflicting reference. Do not submit snapshot IDs or profile/assessment digests; validation calculates and signs those outputs. Only `unit_conversion@1` may be submitted as derived, and only when the generated live contract can be satisfied exactly.

When capabilities advertise `product-presentation@1`, keep the `product@2` or `product@3` entity submission unchanged and add presentation data only through the advertised route wrapper. Use only Colors, Dimensions, and Material Finish as selectable axes. Put unsupported shared facts in all-variant Technical Data; put non-selectable varying facts in combination-scoped Technical Data; split records when an unsupported field is required to order distinct manufacturer identifiers. Submit exact documented combinations, stable deterministic IDs, structured dimension thickness, typed source identities, explicit SKU origin, group scope by combination ID, and applicability evidence. Use the same presentation envelope for validation and staging. Include its topology manifest, canonical `product_structure_digest`, and per-record presentation digests when creating the job. A changed topology, option tuple, scope, warning, or record count requires revalidation and a refreshed confirmation summary.

Before validation, calculate the supported-axis tuple for every typed source identity and prove the tuples are one-to-one within each proposed parent record. Never create a selectable SKU, article, product-code, item-code, `documented-sku`, canonical-URL, or synthetic exact-state axis and never disguise one with the Colors, Dimensions, or Material Finish preset. If two distinct identities collapse to the same supported-axis tuple, or an identity lacks a required supported-axis value, split the affected topology without losing identities, ask for confirmation, or explicitly exclude the parent. Read `max_combinations_per_output_parent` and its digest from live capabilities; fail closed when the limit is missing or inconsistent. A numeric ceiling is not permission to truncate, sample, or relabel source identity as a supported axis.

Treat the capability-advertised presentation version as authoritative. Under `product-presentation@2` or later, bind one explicit primary image-bearing selector axis and assign every enabled documented combination exactly one image-resolution state: `exact_combination_override`, `inherited_selector_value`, `parent_fallback`, or `unresolved`. An exact override requires identity- or tuple-specific official evidence and outranks selector inheritance. Selector inheritance requires an evidenced image on the selected primary option value. Parent fallback is allowed only when the source supports that role and the payload opts in explicitly. An unresolved combination must stay image-less, suppress parent fallback, and appear in the topology unresolved nodes. Never derive exact combination ownership from a filename, URL slug, visual similarity, selector representative identity, or nearby card.

When `product-presentation@3` is advertised, use its evidence-bound `media_references` and `parts` instead of inferring ownership during staging. Preserve stable media/part IDs, exact owner kind and ID, role, supplied URL byte string, order, and evidence. Map option, combination, product, project, part, wireframe, and technical-drawing roles exactly as the live contract advertises. A part image must depict or explicitly bind the physical part; missing exact part evidence leaves it image-less. Keep modern master parts and per-combination BOM entries logically singular rather than duplicating the same part into legacy material parts.

Before validation, calculate the canonical digest of the exact `product_presentation.product_structure`, include it as `product_structure.product_structure_digest` in the complete compact immutable descriptor, and call `specsket_plan_product_ingestion_jobs`. Job manifests contain parent product IDs only. The planner returns both `partition_digest` (the compact partition plan) and `structure_digest` (the exact Product Wizard topology); pass `structure_digest`, never `partition_digest`, in `media_preflight_binding`. Treat `fits_record`, `fits_job`, and `fits_chunk` as independent outcomes; validation chunks are not topology partitions. If the job-wide unresolved structure exceeds its limit, accept only deterministic parent-boundary partitions, never split one parent, rebuild an independently valid structure/checkpoint for each proposed job, recalculate its canonical structure digest, and rerun the planner before validation. URL digests are equality counters only: preserve submitted URLs byte-for-byte and never treat a URL digest as a fetchable URL or a pre-fetch content hash. Request validation advisory metadata for the exact unchanged chunk and report `fits_job: unknown` whenever the complete repeated topology binding is absent.

When capabilities advertise `product-variant-applicability@1`, build that sidecar automatically for every product URL or file ingestion; the user does not need to call it separately. Apply it generically to every relevant Technical Data group/card, installation item, Download entry in every section, and compatible-product relationship. Discover all relevant features rather than an allowlist such as slip/use/3D Ink: include material, performance, technology, premium features, certifications, instructions, documents/references, and relationships wherever official evidence exposes them. Classify each source occurrence as `normalized`, `excluded`, or `unresolved`; use `all_variants` only with evidence that it is shared, use exact documented combination IDs and SKU aliases for scoped facts, and never guess scope. Technical groups bind their existing presentation-group scope instead of duplicating it. Preserve stable occurrence IDs and exact content/applicability evidence so repeated labels remain separately accountable and compatible relationships can aggregate multiple evidence occurrences without duplicating the relationship.

Download extraction is not upload-only. Normalize both obtained files and source references that have a title, description, availability, official source-page URL, and applicability even when no direct file URL exists. Keep certificates in Download as file/reference entries; keep non-document technical features in Technical Data & Specification. Installation and compatible-product entries use the same all/specific/unresolved applicability semantics. A user may later create or edit these file/reference entries manually without fabricating a file.

Build a source-image inventory before mapping media. Put only canonical parent/product images in `media.images`; keep project/application scenes in `media.project_images`, selector-value images on their presentation option values, and exact combination images on their presentation combinations. Attach an exact evidence locator to every image association. Report physical source counts separately from logical parent, selector, combination, project, duplicate, excluded, and unresolved associations, and reconcile the combination coverage totals before validation.

Fail closed before job creation unless the callable tool declarations preserve `product_presentation`, `product_variant_applicability`, `chunk_index`, `topology_manifest`, `destination_plan`, `external_record_ids`, validation receipts, content/request digests, and the required presentation/applicability binding inputs for the advertised contract. A schema document that describes those fields does not compensate for a host adapter that strips them. One compatibility exception is allowed for `destination_plan.destination_contract_version`: when the live capabilities return `destination_contract_binding: server_default_when_omitted`, the callable declaration may omit only that nested version field because the MCP deterministically inserts the simultaneously advertised `destination_contract_version` before request-digest verification and persistence. The destination plan itself and every routing field must still be callable; any other missing field remains a hard stop.

Inspect every provided file available in the current conversation. Preserve the source filename, MIME type, original-byte SHA-256 when the host exposes the bytes, and exact per-field locator. Use taxonomy search for functional categories and CSI rather than freehand IDs.

Validate the complete submission. Resolve every error through the same schema/taxonomy/validation path. Warnings may be presented to the user but must not be silently discarded. Immediately before each staged chunk, refresh its validation receipt when less than 120 seconds remain; unchanged revalidation does not need a second confirmation, but any changed warnings, mappings, assessment, destination, or count does.

For project-aware designer research, keep the product submission and all live Specsket product fields unchanged. Compose them only through the advertised `project-product-validation@1`, `project-product-job-create@1`, and `project-product-stage@1` tools. Preserve the brief receipt, current context binding, complete job-wide external-record/assessment-digest manifest, and exact chunk assessment payloads. Every assessment evidence reference must be owned by that same product record. Do not stage a `blocked` or `insufficient_evidence` assessment. A context or access change quarantines the job and requires a new ChatGPT search; never silently detach the candidate into ordinary ingestion.

For a platform-admin principal, resolve destinations before validation with `specsket_resolve_product_vendor`. Never infer ownership from brand or manufacturer and never create a vendor account as a side effect of staging. Submit all unique external record IDs with one default route and optional per-record overrides; expand that plan into the same full immutable `record_manifest` and digest for every validation chunk. Use `vendor` only for an unambiguous selectable company, `warehouse` only when the real vendor is genuinely unknown, and `unassigned` when an administrator must decide later. The `warehouse` mode always means the configured platform catalog owner; another independently managed vendor with the same display name must be selected by its exact vendor ID in `vendor` mode. Warehouse and unassigned are review states: unassigned blocks approval, while Warehouse requires explicit unknown-vendor acknowledgement and retains unresolved custody history. A later admin assignment creates a new revision and does not rewrite the staged manifest.

If resolution confirms that the product organization is absent and capabilities enable `vendor_onboarding`, keep the product destination unassigned and offer a separate governed onboarding proposal after product staging. Use the server-returned onboarding resolution candidates and digest; do not turn supplier onboarding into vendor creation. Link only completed platform-admin product-ingestion candidates returned by Specsket, validate the proposal, show the exact identity/storefront/product scope, and obtain a new explicit confirmation immediately before staging the vendor-onboarding review. Vendor creation, activation, storefront application, destination changes, and product approval remain separate in-app decisions.

Before calling a write tool, summarize the exact records and effects of that single phase. Obtain separate explicit confirmation immediately before discovery-scope upload/finalization, execution or job creation, each staging operation, and execution or job completion; never treat an earlier confirmation as authorization for a later phase. For a vendor principal, name the target vendor. For a designer principal, state that the records enter that designer's private review queue and cannot be assigned to a vendor. For a project-aware designer job, also show the exact project, selected rooms, context revision, fit classifications, and that approval means **Approve to My Library** only. For a platform admin, state that OAuth remains platform-scoped and does not create a vendor, user, store, or membership. After completion, explain the 60-second signed-in link and obtain a separate confirmation before link creation or browser opening; an account switch always requires its own visible confirmation.

After confirmation, create the job, stage the exact validated records, inspect all results, and complete the job. Always print the permanent `review_url`. Then call `specsket_create_review_session` with the completed `job_id` and the first accepted `domain_record_id` the user should review. Print an **Open signed-in Specsket review** link using `browser_launch_url`, note its expiry, and ask the host to open that URL in the visible in-app browser when available. Never say that the browser opened unless the browser action returned success. If browser opening is unavailable or fails, keep the signed-in link clickable and repeat the permanent fallback URL. Never put the browser ticket anywhere else or claim it is permanent.

Never call supplier onboarding tools for a product error. Never publish, approve, directly mutate product tables, or claim an import succeeded before job completion returns a review URL. If the signed-in link expires, create another only after the user asks to open the completed review again.
