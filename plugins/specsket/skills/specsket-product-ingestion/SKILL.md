# Specsket product ingestion

Use this skill only for the `product_ingestion` workflow and `product` entity.

Use the strict validated product workflow by default for imports, including requests to extract deeply, populate product fields, include variants, or stage complete products. The user does not need to say “strict.” Recovery availability is not a reason to downgrade those requests. Use the [recovery capture contract](../../references/product-recovery-capture-contract.md) only when the user explicitly requests incomplete review drafts and its three operations are advertised. For that path only, its preparation/confirmation/staging procedure replaces the strict write sequence below. Research, exact evidence, truthful completeness, destination authorization, and separate human approval remain mandatory. Never strip an existing governed envelope or switch paths to evade authorization, project-assessment, checksum, digest, or receipt failures. Preserve existing signed captures and successful candidates; corrections must not silently duplicate products.

## Strict sequence at a glance

This is the whole write path. Never compute or type an id or digest that Specsket can derive (even when your host can run code). When the host saves a large result to a file, read only the parts you need from that file. You author content and natural keys; Specsket derives ids and digests and returns them. Copy values only from responses.

0. Authoring kit. When `specsket_get_product_authoring_kit` is listed, read it in its two parts: `part: core` carries the principal and workflow gates, the ingestion contracts (its `contracts.product_discovery_scope` is the capabilities `product_discovery_scope_contract`), planning limits, the current entity fields and submission contract and `authoring_shapes`; `part: presentation` carries the presentation wrapper schemas (read it before writing `product_presentation` and its sidecars). Otherwise call `specsket_get_capabilities`, then read the `current` entity schema (with presentation contracts when advertised) and the research contract. The derived flow needs `product_discovery_scope_contract.server_derivation`, `product_discovery_scope_contract.chunk_digest_derivation` and `product_discovery_scope_contract.chunk_id_derivation` all true. If any is absent (older Specsket), ids and digests must be supplied by the client: stop and tell the user rather than guess hashes you cannot compute. Use taxonomy search for categories.
1. Source inventory from rendered pages and every linked official document; account for every active catalog field (ingestion preview contract: "Field coverage and source documents").
2. Scope. Choose a parent-topology scope (`bounded` prefix or `all_discovered`) in ONE fragment. Upload the fragment with natural keys only: `key` on source parents and orderable variants, `key:<k>` references to them inside the same fragment, and inline `evidence` / `source` objects on evidence bindings. Omit every derivable id and digest (including `authority_key` and `source_parent_id` on source parents, `orderable_variant_id`, `partition_digest` and a partition's `evidence_refs`: a hand-computed value that differs fails the upload), but keep the authored `evidence_ref` and `source_id` on each evidence binding. Upload with `capability_digest` copied from capabilities `product_ingestion_planning_limits.digest`. Finalize with the `scope_id` and `open_execution: { idempotency_key }` (your own key) when the finalize tool lists it: one call, one confirmation, and the response carries `execution` (its `id` and `execution_receipt`) instead of a scope receipt. Otherwise finalize with the header only (or the `scope_id`) and create the execution with `scope_id`, `scope_root_digest` and `scope_receipt` (both from the finalize response; the digest is `scope.root_digest`), the same `capability_digest`, your own idempotency key, and `partitions`/`assignments` omitted. Use an absolute, stable `checkpoint_ref` per partition. The execution response returns NO partitions: take `id` (the execution id) and `execution_receipt` from it, and `partition_id` and `partition_digest` from the upload response `server_derived.execution_partitions` entry whose `partition_id` matches. Every source in a chunk must be bound by a partition evidence binding of the scope, and the inline `evidence`/`source` objects must be identical in the scope fragment and the chunk; otherwise job creation fails with a 409 without `expected`, and since fragments are immutable the scope must be re-created. Size partitions at 1-2 heavy products up front. Omit a variant's `orderable_variant_id` and a partition's `evidence_refs` and a current server derives them (the canonical identity is added to the aliases; the partition evidence is the union of its parents' and selected variants' refs); a supplied value must match exactly (see [ingestion validation gotchas](../../references/ingestion-validation-gotchas.md)).
3. Per chunk (one partition = one job = one chunk, 1-2 heavy products), author `product@3`, presentation, applicability, `product-source-coverage@2` and readiness. Give every presentation object an `external_key`, reference objects in the same record as `key:<external_key>`, and omit ids, generated SKUs, group/occurrence ids and every digest. For combination and selector images give only `image_urls` / `image_url` with `evidence_refs` and leave out `image_media_reference_ids`, `image_media_reference_id` and their `media_references` entries: the server creates them (author media references only for the product primary, project, part and drawing images). Never reuse a key for a different thing; renaming an `external_key` changes every id derived from it. An applicability occurrence's `native_pointer` is a JSON pointer into the saved draft, not a path into your request: `/custom_parameter_groups/<n>` for a technical group and `/technical_files/<n>` (or `/documents/<n>`) for a download; when unsure, send once and copy `issues[].expected`. Applicability occurrences for technical groups (and other presentation groups) need an authored `source_locator_key`: any stable string unique per occurrence within the record (e.g. `grp-<external_key>`); it feeds the derived occurrence id, so keep it identical on retries and never reuse it for another occurrence. In `product-source-coverage@2` copy `discovery_scope_digest` (finalize `scope.root_digest`), `execution_id` (the execution response `id`), `execution_partition_id` and `execution_partition_digest` (matching upload `server_derived.execution_partitions` entry); you still author `completeness_scope`, `completion_status` and the counts. `key:` references are NOT resolved in chunk sidecars: coverage `source_parent_id` and `orderable_variant_ids`, and readiness `grouping.source_parent_id` and `represented_orderable_variant_id`, must be the real `sp:`/`ov:` ids copied from the scope upload response `server_derived.source_parents[]` (`source_parent_id`, and each `orderable_variants[].orderable_variant_id`), matched by the `key` you gave that parent/variant.
4. Validate the chunk. Write observations, trace entries, relationships and profiles to the kit's `authoring_shapes` schemas (exact validators: no extra keys, only the listed enum words; leave out the `server_fills` keys). Before the first call read [ingestion validation gotchas](../../references/ingestion-validation-gotchas.md): its "Copy these shapes" block (copy the observation, trace and relationship entries; do not write them from memory) and its "Quality gate" (spec tables as groups, notes, per-size documents) and the metadata, enum and image rules the schema omits. Passing validation does not mean the listing is complete. Copy from the response: the signed receipt, `job_binding` (`topology_manifest`, per-record digest maps, `product_structure_digest`, `record_manifest_digest`, the suggested `job` block), `request_digest` and `derived.key_to_id`. `job_binding` is complete only when `single_chunk` is true; if false, stop and tell the user (multi-chunk jobs cannot be built plugin-only). Plugin-only agents do not call `specsket_plan_product_ingestion_jobs`; the digest comes from `job_binding`. Read `derived.values` (including `repaired` and `profile_lists_extended`) before staging: if the server filled or changed a value you did not intend, such as a unit added to a profile or a replaced `normalized_context`, fix the source of the mistake and validate again.
5. When `specsket_stage_validated_chunk` is listed and `job_binding.single_chunk` is true, steps 5 and 6 are one call (one confirmation for job creation and staging): pass the validate answer's `chunk_cache.handle`, the `execution_receipt`, and your own `job_idempotency_key`, `operation_id` and `chunk_idempotency_key` (write them down first; a retry repeats the identical call, including the same `execution_receipt`, and resumes the saved job and intent). It creates the job, prepares the stage intent and dispatches; if dispatch is refused (for example storage not yet enrolled by the owner) the prepared intent is kept and you dispatch it later with `specsket_dispatch_product_chunk_stage_intent`; an `unknown` outcome is reconciled first, never re-sent. Otherwise, create the job with `job_binding.job` and `job_binding.topology_manifest`, plus: `schema_version` and `taxonomy_versions` from your own submission (leave out `source_manifest`: with `execution_binding` the server takes exactly the partition's sources from the scope; supply it only when the server answers that it is required, as your submission's `sources`); your own idempotency key; and `execution_binding` = `execution_id` (the execution response `id`), `execution_partition_id`, `execution_partition_digest`, `discovery_scope_digest`, `execution_receipt` (values from step 2). `request_digest` and the manifest digests may be omitted. Create the job and stage within the execution receipt's life (about ten minutes, see `execution_receipt_expires_at`).
6. (When the validate answer carries `chunk_cache.handle`, send corrections as `base_chunk` plus `patch` and stage with `chunk_handle` rather than resending the chunk; see the gotchas reference.) Stage with the job id (when capabilities report `product_chunk_stage_intent.enabled`, stage through `specsket_prepare_product_chunk_stage_intent` then `specsket_dispatch_product_chunk_stage_intent` per the workflow contract, not `specsket_stage_validated_records`), `chunk_index`, your own chunk idempotency key, the identical authored payload and the validation receipt. `content_digest` is optional (it equals validation's `request_digest`). Any change to the payload needs a new validation.
7. A timeout or lost response is not a failed write. Call `specsket_reconcile_product_ingestion_chunk` with the same job, chunk index and idempotency key before anything else; never stage again with a new key or a different payload for the same chunk.
8. Complete the job with `complete_execution_id` (the execution id) to close the execution in the same call (one confirmation; the execution closes only when all its partition jobs are complete, otherwise the answer says so), or complete the job and then the execution. Print the permanent review URL.

Plugin-only limits (say them to the user when they bite): a multi-fragment scope needs `header.total_canonical_bytes` up front, which you cannot compute, so keep the scope to one fragment; `exact_identity_subset` needs client-supplied `ov:` identity keys, so it is not available plugin-only; `source.content_sha256` of external bytes is not derivable, so omit it unless the host exposes the bytes. Classification and applicability outcomes, coverage counts and readiness bindings stay your judgement from evidence and are never defaulted to `all_variants`. Plugin users should omit derivable values rather than supply them; a wrong supplied value is rejected (with `issues[].expected`) only on paths where the server can derive it.

Chunk size and time: Specsket cancels a chunk write that runs too long and the advertised record cap is only a schema limit, so do not fill chunks to it. Validation receipts expire after about ten minutes; re-validate an unchanged payload instead of staging an expired receipt.

Distributed brands: before authoring a copy of another maker's product, check whether the maker has an active Specsket company that already published it (`specsket_search_products` with `vendor_ids`). A published product can be linked into the distributor's storefront through the vendor-authoring link flow (for a company connection that offers it) instead of being copied; keep a copy, with brand and manufacturer evidence, only when the maker has no company or no published product.

Classification and images (learned in live runs):
- `product_types` accepts only the system types `Material` (building products) and `FF&E` (furniture, fixtures and equipment). Put the supplier or category label ("Raised access floor", "Crash cushion") in `product_subtypes`. Validation reports `product_types_not_system_type` for a record or profile that breaks this; an approved candidate cannot carry a supplier label. If the type is genuinely unclear, leave `product_types` out and say why.
- An image URL that returns HTTP 200 and an image Content-Type is not enough evidence. Prefer URLs whose bytes you could confirm are really an image. Specsket accepts a valid image whose declared type differs from its bytes (for example a JPEG served as `image/webp`) and only counts it in telemetry, but it still rejects unknown bytes, HTML and SVG. Do not use a URL you saw only as a page or thumbnail.
- If a dispatch response carries `last_attempt` (a code such as `integration_image_invalid_image` and `issue_codes`), the stage attempt failed and the original is still unresolved: read the original intent and job and reconcile; fix the named problem (for example replace the image) in a fresh attempt only when the original is proven uncommitted. `last_attempt` is a diagnostic, never proof of non-commitment.
- Author the payload and dispatch in the same hour. An execution or validation receipt older than about ten minutes needs refreshing, and a prepared intent that waited longer can have its permission renewal denied (`chunk_permission_renewal_denied`, not retryable); then start a fresh scope, execution and job instead of retrying. Write down the ids as soon as the intent is prepared so an interrupted session can resume without creating a duplicate.

Troubleshooting:
- A timeout, 502 or 120 s tool cutoff is not a failed write: reconcile by job + chunk + idempotency key, then wait and reconcile again.
- Chunk persistence timeout (57014): abandon the job and start a new scope with smaller partitions (1-2 heavy products each); one partition = one job = one chunk, and never send a different payload under the old key.
- Receipt older than ~10 minutes or under 120 s left: re-validate the same payload.
- `issues[].expected` holds the correct value for a wrong supplied id or digest; follow-on errors are suppressed only for the `content_digest`/`occurrence_id` paths that could not be derived, other real errors can still be listed. Copy `expected`, or simply omit the field.
- Renaming an `external_key` changes every id derived from it, so a retry with a renamed key is a different record.
- Execution receipt expired (about ten minutes): call `specsket_refresh_product_ingestion_execution_receipt` with the execution id; a stale validation receipt is re-validated.
- Duplicate or unknown `key:` errors name the key: keys must be unique per kind within a record, and a `key:` reference must name an `external_key` in the same record.
- `single_chunk: false` in `job_binding`: the job cannot be bound plugin-only; stop and ask the user.

When `specsket_get_ingestion_candidate_summary` is listed, call it for each accepted `domain_record_id` after staging: it returns a URL-free summary of the staged candidate (name, brand, manufacturer, classification labels, and counts of images, documents, variants, technical properties and installation entries) so you can compare saved against source without the admin UI. Report any count that is lower than the source; zero counts for installation or documents mean nothing was saved under the native roots it checks, not that the source had none. It cannot approve or publish.

Before calling any batch complete, reconcile source data to actual saved product fields. Check primary/gallery images, exact documented variant identities and supported-axis tuples, technical groups, instructions, documents and applicability, and every source-backed field in the live catalog. State unavailable or unresolved values with evidence and reasons instead of inventing them. Source JSON, retained arrays, local downloads, accepted record counts, and successful saves are not proof of imported images, native variants, or transferred files. Inspect a saved representative candidate for every vendor and page shape before continuing a batch; then verify every record's source-to-saved counts. If the representative lacks source-backed fields, fix the mapping and verify it before continuing.

Before the first field preview, read [the extraction and authoring rules](../../references/ingestion-authoring-rules.md) in full: rendered-page extraction and visible source review, official documents and certification accounting, the live schema and the pre-validation preview, the topology choice, discovery scope and readiness, profiles and technical properties, presentation versions, variant tuples, applicability, downloads and images, and the host checks before job creation. They are part of this skill.

Before calling a write tool, summarize the exact records and effects of that single phase. Obtain separate explicit confirmation immediately before discovery-scope upload/finalization, execution or job creation, each staging operation, and execution or job completion (finalizing with `open_execution` is one phase: one confirmation that names both the frozen scope and the opened execution; `specsket_stage_validated_chunk` is one phase: one confirmation that names the job and the staging of its records into review, or pass `dispatch: false` to confirm dispatch separately); never treat an earlier confirmation as authorization for a later phase. For a vendor principal, name the target vendor. For a designer principal, state that the records enter that designer's private review queue and cannot be assigned to a vendor. For a project-aware designer job, also show the exact project, selected rooms, context revision, fit classifications, and that approval means **Approve to My Library** only. For a platform admin, state that OAuth remains platform-scoped and does not create a vendor, user, store, or membership. After completion, explain the 60-second signed-in link and obtain a separate confirmation before link creation or browser opening; an account switch always requires its own visible confirmation.

After confirmation, create the job, stage the exact validated records, inspect all results, and complete the job. Always print the permanent `review_url`. Then call `specsket_create_review_session` with the completed `job_id` and the first accepted `domain_record_id` the user should review. Print an **Open signed-in Specsket review** link using `browser_launch_url`, note its expiry, and ask the host to open that URL in the visible in-app browser when available. Never say that the browser opened unless the browser action returned success. If browser opening is unavailable or fails, keep the signed-in link clickable and repeat the permanent fallback URL. Never put the browser ticket anywhere else or claim it is permanent.

Never call supplier onboarding tools for a product error. Never publish, approve, directly mutate product tables, or claim an import succeeded before job completion returns a review URL. If the signed-in link expires, create another only after the user asks to open the completed review again.
