# Specsket product ingestion

Use this skill only for the `product_ingestion` workflow and `product` entity.

Use the strict validated product workflow by default for imports, including requests to extract deeply, populate product fields, include variants, or stage complete products. The user does not need to say “strict.” Recovery availability is not a reason to downgrade those requests. Use the [recovery capture contract](../../references/product-recovery-capture-contract.md) only when the user explicitly requests incomplete review drafts and its three operations are advertised. For that path only, its preparation/confirmation/staging procedure replaces the strict write sequence below. Research, exact evidence, truthful completeness, destination authorization, and separate human approval remain mandatory. Never strip an existing governed envelope or switch paths to evade authorization, project-assessment, checksum, digest, or receipt failures. Preserve existing signed captures and successful candidates; corrections must not silently duplicate products.

## Strict sequence at a glance

This is the whole write path. Never compute or type an id or digest that Specsket can derive (even when your host can run code). When the host saves a large result to a file, read only the parts you need from that file. You author content and natural keys; Specsket derives ids and digests and returns them. Copy values only from responses.

0. Capabilities. Call `specsket_get_capabilities`. The derived flow needs `product_discovery_scope_contract.server_derivation`, `product_discovery_scope_contract.chunk_digest_derivation` and `product_discovery_scope_contract.chunk_id_derivation` all true. If any is absent (older Specsket), ids and digests must be supplied by the client: stop and tell the user rather than guess hashes you cannot compute. Then read the `current` entity schema (with presentation contracts when advertised), the research contract and taxonomy search.
1. Source inventory from rendered pages and every linked official document; account for every active catalog field (ingestion preview contract: "Field coverage and source documents").
2. Scope. Choose a parent-topology scope (`bounded` prefix or `all_discovered`) in ONE fragment. Upload the fragment with natural keys only: `key` on source parents and orderable variants, `key:<k>` references to them inside the same fragment, and inline `evidence` / `source` objects on evidence bindings. Omit every derivable id and digest, but keep the authored `evidence_ref` and `source_id` on each evidence binding. Upload with `capability_digest` copied from capabilities `product_ingestion_planning_limits.digest`. Finalize with the header only (or the `scope_id`). Create the execution with `scope_id`, `scope_root_digest` and `scope_receipt` (both from the finalize response; the digest is `scope.root_digest`), the same `capability_digest`, your own idempotency key, and `partitions`/`assignments` omitted. Use an absolute, stable `checkpoint_ref` per partition. The execution response returns NO partitions: take `id` (the execution id) and `execution_receipt` from it, and `partition_id` and `partition_digest` from the upload response `server_derived.execution_partitions` entry whose `partition_id` matches. Every source in a chunk must be bound by a partition evidence binding of the scope, and the inline `evidence`/`source` objects must be identical in the scope fragment and the chunk; otherwise job creation fails with a 409 without `expected`, and since fragments are immutable the scope must be re-created. Size partitions at 1-2 heavy products up front.
3. Per chunk (one partition = one job = one chunk, 1-2 heavy products), author `product@3`, presentation, applicability, `product-source-coverage@2` and readiness. Give every presentation object an `external_key`, reference objects in the same record as `key:<external_key>`, and omit ids, generated SKUs, group/occurrence ids and every digest. Never reuse a key for a different thing; renaming an `external_key` changes every id derived from it. Applicability occurrences for technical groups (and other presentation groups) need an authored `source_locator_key`: any stable string unique per occurrence within the record (e.g. `grp-<external_key>`); it feeds the derived occurrence id, so keep it identical on retries and never reuse it for another occurrence. In `product-source-coverage@2` copy `discovery_scope_digest` (finalize `scope.root_digest`), `execution_id` (the execution response `id`), `execution_partition_id` and `execution_partition_digest` (matching upload `server_derived.execution_partitions` entry); you still author `completeness_scope`, `completion_status` and the counts. `key:` references are NOT resolved in chunk sidecars: coverage `source_parent_id` and `orderable_variant_ids`, and readiness `grouping.source_parent_id` and `represented_orderable_variant_id`, must be the real `sp:`/`ov:` ids copied from the scope upload response `server_derived.source_parents[]` (`source_parent_id`, and each `orderable_variants[].orderable_variant_id`), matched by the `key` you gave that parent/variant.
4. Validate the chunk. Copy from the response: the signed receipt, `job_binding` (`topology_manifest`, per-record digest maps, `product_structure_digest`, `record_manifest_digest`, the suggested `job` block), `request_digest` and `derived.key_to_id`. `job_binding` is complete only when `single_chunk` is true; if false, stop and tell the user (multi-chunk jobs cannot be built plugin-only).
5. Create the job with `job_binding.job` and `job_binding.topology_manifest`, plus: `schema_version`, `taxonomy_versions` and `source_manifest` (your submission's `sources`) from your own submission; your own idempotency key; and `execution_binding` = `execution_id` (the execution response `id`), `execution_partition_id`, `execution_partition_digest`, `discovery_scope_digest`, `execution_receipt` (values from step 2). `request_digest` and the manifest digests may be omitted. Create the job and stage within the execution receipt's life (about ten minutes, see `execution_receipt_expires_at`).
6. Stage with the job id, `chunk_index`, your own chunk idempotency key, the identical authored payload and the validation receipt. `content_digest` is optional (it equals validation's `request_digest`). Any change to the payload needs a new validation.
7. A timeout or lost response is not a failed write. Call `specsket_reconcile_product_ingestion_chunk` with the same job, chunk index and idempotency key before anything else; never stage again with a new key or a different payload for the same chunk.
8. Complete the job, then the execution, and print the permanent review URL.

Plugin-only limits (say them to the user when they bite): a multi-fragment scope needs `header.total_canonical_bytes` up front, which you cannot compute, so keep the scope to one fragment; `exact_identity_subset` needs client-supplied `ov:` identity keys, so it is not available plugin-only; `source.content_sha256` of external bytes is not derivable, so omit it unless the host exposes the bytes. Classification and applicability outcomes, coverage counts and readiness bindings stay your judgement from evidence and are never defaulted to `all_variants`. Plugin users should omit derivable values rather than supply them; a wrong supplied value is rejected (with `issues[].expected`) only on paths where the server can derive it.

Chunk size and time: Specsket cancels a chunk write that runs too long and the advertised record cap is only a schema limit, so do not fill chunks to it. Validation receipts expire after about ten minutes; re-validate an unchanged payload instead of staging an expired receipt.

Distributed brands: before authoring a copy of another maker's product, check whether the maker has an active Specsket company that already published it (`specsket_search_products` with `vendor_ids`). A published product can be linked into the distributor's storefront through the vendor-authoring link flow (for a company connection that offers it) instead of being copied; keep a copy, with brand and manufacturer evidence, only when the maker has no company or no published product.

Classification and images (learned in live runs):
- `product_types` accepts only the system types `Material` (building products) and `FF&E` (furniture, fixtures and equipment). Put the supplier or category label ("Raised access floor", "Crash cushion") in `product_subtypes`. Validation reports `product_types_not_system_type` for a record or profile that breaks this; an approved candidate cannot carry a supplier label. If the type is genuinely unclear, leave `product_types` out and say why.
- An image URL that returns HTTP 200 and an image Content-Type is not enough evidence. Prefer URLs whose bytes you could confirm are really an image. Specsket accepts a valid image whose declared type differs from its bytes (for example a JPEG served as `image/webp`) and only counts it in telemetry, but it still rejects unknown bytes, HTML and SVG. Do not use a URL you saw only as a page or thumbnail.
- If a dispatch response carries `last_attempt` (a code such as `integration_image_invalid_image` and `issue_codes`), the stage attempt failed and the original is still unresolved: read the original intent and job and reconcile; fix the named problem (for example replace the image) in a fresh attempt only when the original is proven uncommitted. `last_attempt` is a diagnostic, never proof of non-commitment.
- Author the payload and dispatch in the same hour. An execution or validation receipt older than about ten minutes needs refreshing, and a prepared intent that waited longer can have its permission renewal denied (`chunk_permission_renewal_denied`, not retryable); then start a fresh scope, execution and job instead of retrying. Write down the ids as soon as the intent is prepared so an interrupted session can resume without creating a duplicate.

Troubleshooting:
- A timeout, 502 or 120 s tool cutoff is not a failed write: reconcile by job + chunk + idempotency key, then wait and reconcile again.
- Chunk persistence timeout (57014): abandon the job and start a new scope with smaller partitions (1-2 heavy products each); one partition = one job = one chunk, and never send a different payload under the old key.
- Receipt older than ~10 minutes or under 120 s left: re-validate the same payload.
- `issues[].expected` holds the correct value for a wrong supplied id or digest; follow-on errors are suppressed only for the `content_digest`/`occurrence_id` paths that could not be derived, other real errors can still be listed. Copy `expected`, or simply omit the field.
- Renaming an `external_key` changes every id derived from it, so a retry with a renamed key is a different record.
- Execution receipt expired (about ten minutes): call `specsket_refresh_product_ingestion_execution_receipt` with the execution id; a stale validation receipt is re-validated.
- Duplicate or unknown `key:` errors name the key: keys must be unique per kind within a record, and a `key:` reference must name an `external_key` in the same record.
- `single_chunk: false` in `job_binding`: the job cannot be bound plugin-only; stop and ask the user.

When `specsket_get_ingestion_candidate_summary` is listed, call it for each accepted `domain_record_id` after staging: it returns a URL-free summary of the staged candidate (name, brand, manufacturer, classification labels, and counts of images, documents, variants, technical properties and installation entries) so you can compare saved against source without the admin UI. Report any count that is lower than the source; zero counts for installation or documents mean nothing was saved under the native roots it checks, not that the source had none. It cannot approve or publish.
