# Specsket product ingestion

Use this skill only for the `product_ingestion` workflow and `product` entity. Rows that match a product already in Specsket (same SKU or name; see `possible_duplicates`) are updated with the vendor-authoring skill, not re-ingested.

Use the strict validated product workflow by default for imports, including requests to extract deeply, populate product fields, include variants, or stage complete products. Use the [recovery capture contract](../../references/product-recovery-capture-contract.md) only when the user explicitly requests incomplete review drafts and its three operations are advertised; its procedure then replaces the strict write sequence below. Research, evidence, truthful completeness, destination authorization and human approval remain mandatory. Never strip an existing governed envelope or switch paths to evade authorization, project-assessment, checksum, digest, or receipt failures. Preserve existing signed captures and successful candidates; corrections must not silently duplicate products.

Respect robots.txt and site access refusals: on a 401, 403 or 429 or a robots disallow, do not retry with a different User-Agent, headers, proxy or mirror; record the source as unavailable and tell the user.

When a Specsket tool is listed but not loaded, load its schema with ToolSearch before its first call; an error that says a field is "Required" on a tool you have not loaded means its schema was not loaded. If you cannot open the files linked here (no file access), do not stop: author from the kit's `authoring_shapes` and `authoring_rules` and the `expected` values in every error. The first validate is a safe, read-only way to get the exact fixes, and every confirmation below still applies. Do not tell the user a file was missing unless a rule you need is not stated here.

## What to read, and when

Each step below starts with the references to read before it; read each when its step starts, not all up front. Every rule in them is as binding as this skill. Read these only when their situation applies:
- the matching file in [rules for specific situations](../../references/ingestion-conditional-rules.md): an older Specsket without `product_discovery_scope_contract`, a host that computes canonical digests, a platform-admin principal, project-aware designer research, an original refused before native writes or whose permission expired, no live Specsket connection, or no authoring kit;
- a numbered step of the workflow contract's "Visible source review" when this skill or a reference names it;
- [the installation and download field rules](../../references/evidence-installation-downloads.md) when you write installation entries or downloads;
- [staging recovery](../../references/staging-recovery.md) and the evidence contract's "Original operation outcome evidence", when that outcome occurs;
- [the field catalog contract](../../references/field-catalog-contract.md) when the user asks which fields exist or you need the `field_catalog` shape.

## Strict sequence at a glance

This is the whole write path. You author content and natural keys; Specsket derives ids and digests and returns them. Never compute or type an id or digest Specsket can derive (even when your host can run code); copy values only from responses. When the host saves a large result to a file, read only the parts you need.

0. With file access, read first: [the visible source review](../../references/visible-source-review.md) and the "Large responses" note in [ingestion staging gotchas](../../references/ingestion-gotchas-staging.md). Read `specsket_get_capabilities` with `focus: "product_ingestion"`. Authoring kit: when `specsket_get_product_authoring_kit` is listed, read it in parts as its own `note` says (everything you read stays in context for every later call): `part: core` now, `part: scope` only at step 2, `part: presentation` only at step 3, `part: legacy` for an older flow or a schema a stub names. Without the kit, read the `current` entity schema (with presentation contracts when advertised) and the research contract. The derived flow needs `product_discovery_scope_contract.server_derivation`, `chunk_digest_derivation` and `chunk_id_derivation` all true; if any is absent, stop and tell the user rather than guess hashes. For functional categories and CSI use one `specsket_search_taxonomy` call with `queries` (2-3 search words) and no `taxonomy`, never freehand ids; copy the returned versions into `taxonomy_versions`. Reuse the research contract while its digest and the connected principal are unchanged.
1. With file access, read first, before the first field preview: [the extraction and authoring rules](../../references/ingestion-authoring-rules.md) in full, [the ingestion preview contract](../../references/ingestion-preview-contract.md), [the evidence contract](../../references/evidence-contract.md), [rendered-page extraction](../../references/rendered-page-extraction.md), and, when capabilities advertise `product-readiness@1`, [the product readiness contract](../../references/product-readiness-contract.md). Inventory the rendered pages and every linked official document; account for every active catalog field. Show the filled and unresolved fields; give the full field list only when the user asks, and do not ask which layout they want.
2. With file access, read first: [ingestion scope gotchas](../../references/ingestion-gotchas-scope.md) and [the discovery-scope evidence rules](../../references/evidence-discovery-scope.md). Scope: read the kit's `part: scope`. Choose a parent-topology scope (`bounded` prefix or `all_discovered`) in ONE fragment and upload it with natural keys only (the kit's scope shapes list them; omit every derivable id and digest, a hand-computed value that differs fails the upload; keep the authored `evidence_ref` and `source_id` on each evidence binding). When `specsket_upload_product_discovery_scope_fragment_from_file` is listed, write the upload to a file in the payload folder and upload from there; never print the file back. Copy later ids from its `server_derived` answer. Send `capability_digest` from capabilities `product_ingestion_planning_limits.digest` and leave `header.total_canonical_bytes` out. Open every variant, size or finish page you will cite and bind each as its own source. `source_frontier_status`: `exhausted` when you found every product asked for (for a category or `all_discovered` scope, every listing page, pagination and subcategory opened) and the opened pages list each one's variants; otherwise `incomplete` with `source_frontier_reason`. Every `evidence_ref` on a parent or variant, and every `evidence_ref` that `source_coverage` will cite (each state, document and certification), needs an `evidence_bindings` entry in this fragment: a finalized scope cannot change. Evidence only fields and the presentation cite goes in the chunk's own `evidence_catalog`. Size partitions at 1-2 heavy products. Finalize with the `scope_id` and `open_execution: {}` when the finalize tool lists it (a retry replays; after a failed job send `open_execution: { replaces_execution_id }`): one call, covered by the draft confirmation; the response carries `execution` (`id`, `execution_receipt`). Otherwise finalize, then create the execution with `scope_id`, `scope_root_digest` and `scope_receipt` from the finalize response, the same `capability_digest` and your own idempotency key. Use an absolute, stable `checkpoint_ref` per partition. Take `partition_id` and `partition_digest` from the upload's `server_derived.execution_partitions`. Any inline `evidence`/`source` a chunk repeats must be identical to the scope's.
3. With file access, read first: [ingestion validation gotchas](../../references/ingestion-validation-gotchas.md); copy its "Copy these shapes" entries (never write them from memory) and answer its "Quality gate". Read the kit's `part: presentation`. Per chunk (one partition = one job = one chunk, 1-2 heavy products), author `product@3`, presentation, applicability, `product-source-coverage@2` and readiness. Give every presentation object an `external_key`, reference objects in the same record as `key:<external_key>`, and omit ids, generated SKUs, group/occurrence ids and every digest. Never reuse a key for a different thing; renaming an `external_key` changes every id derived from it, so a retry with a renamed key is a different record. When capabilities advertise `chunk_scope_evidence_reuse`, leave out of `evidence_catalog` and `sources` what the scope already binds. Every `evidence_refs` entry must be an `evidence_ref` bound in the scope fragment (copy it exactly) or an entry of this chunk's `evidence_catalog`. Write each fact once, following the kit's `authoring_shapes` (`download_written_once`, `spec_table_applicability`, `per_combination_table`, `written_once_more`, `source_coverage_minimal`) and leaving out everything in its `server_fills` list; `completion_status`, unresolved states, classification and applicability outcomes and readiness bindings stay your judgement; a count you do write must match its list. Without `chunk_write_once_3` (older server), follow kit `part: legacy` and the `expected` values in the errors. All of these come from evidence and are never defaulted to `all_variants`. In `product-source-coverage@2` copy `execution_id` and `execution_partition_id` from the execution. `key:` references are NOT resolved in chunk sidecars: coverage `source_parent_id` and `orderable_variant_ids` (when you write them) and readiness `grouping.source_parent_id` and `represented_orderable_variant_id` must be the real `sp:`/`ov:` ids from the scope upload's `server_derived.source_parents[]`, matched by the `key` you gave. An applicability occurrence's `native_pointer` follows the validation gotchas' pointer rule.
4. Validate the chunk inline; when the answer carries `chunk_cache.handle`, send corrections as `base_chunk` plus `patch` and stage with `chunk_handle` (staging gotchas). Write observations, trace entries, relationships and profiles to the kit's `authoring_shapes` schemas (exact validators: no extra keys, only the listed enum words). Passing validation does not mean the listing is complete. Copy from the response the signed receipt, `job_binding` (`topology_manifest`, per-record digest maps, `product_structure_digest`, `record_manifest_digest`, the suggested `job` block), `request_digest` and `derived.values` (compact by default; `verbose: true` only when you need the normalized records). `job_binding` is complete only when `single_chunk` is true; if false, stop and tell the user (multi-chunk jobs cannot be built plugin-only). Plugin-only agents do not call `specsket_plan_product_ingestion_jobs`. Read `derived.values` (including `repaired` and `profile_lists_extended`) before staging; if the server filled or changed a value you did not intend, fix the source of the mistake and validate again.
5. With file access, read first: the rest of [ingestion staging gotchas](../../references/ingestion-gotchas-staging.md). When `specsket_stage_validated_chunk` is listed and `job_binding.single_chunk` is true, steps 5 and 6 are one call (one confirmation for job creation and staging): pass the validate answer's `chunk_cache.handle`, the `execution_receipt`, and your own `job_idempotency_key`, `operation_id` and `chunk_idempotency_key` (write them down first; a retry repeats the identical call and resumes the saved job). It stages through the records route and answers `route: records`: there is no intent and no separate dispatch, the staged chunk goes straight to review, and `dispatch: false` creates the job only. Its `unknown` outcome is reconciled with `specsket_get_ingestion_job` first; a retry repeats the identical call with the same keys, never a new key. After `execution_receipt_expires_at` the call cannot recreate the job, so stage that `job_id` with `specsket_stage_validated_records` and the same chunk idempotency key instead (a chunk already saved under the key is returned, not staged twice). Otherwise, on the default hosted list stop and tell the user; on the operator address or in the local app create the job (kit `part: legacy`, `applicability_job_create`) with `job_binding.job` and `job_binding.topology_manifest`, `schema_version` and `taxonomy_versions` from your submission, your own idempotency key, and `execution_binding` (`execution_id`, `execution_partition_id`, `execution_partition_digest`, `discovery_scope_digest`, `execution_receipt` from step 2); supply `source_manifest` only when the server says it is required. Create the job and stage within the execution receipt's life (about ten minutes).
6. Stage with `specsket_stage_validated_records`: the job id, `chunk_index`, your own chunk idempotency key, the identical authored payload and the validation receipt. Any change to the payload needs a new validation.
7. A timeout, 502, 120 s tool cutoff or lost response is not a failed write (read the workflow contract's paragraph on an uncertain product chunk stage, after its numbered steps). Call `specsket_reconcile_product_ingestion_chunk` with the same job, chunk index and idempotency key before anything else, then wait and reconcile again while it stays unknown; never stage again with a new key or a different payload for the same chunk.
8. Complete the job with `complete_execution_id` (the execution id) to close the execution in the same call, or complete the job and then the execution (the execution closes only when all its partition jobs are complete, otherwise the answer says so). Read workflow contract step 12 before reporting execution status after a reconnect or a completion response (unknown counts stay unknown). Print the permanent review URL.

Plugin-only limits (say them to the user when they bite): a multi-fragment scope needs `header.total_canonical_bytes` up front, which you cannot compute, so keep the scope to one fragment; `exact_identity_subset` needs client-supplied `ov:` identity keys, so it is not available; omit `source.content_sha256` of external bytes unless the host exposes the bytes. A wrong supplied value is rejected (with `issues[].expected`) only on paths where the server can derive it.

Chunk size: Specsket cancels a chunk write that runs too long and the advertised record cap is only a schema limit, so do not fill chunks to it.

Distributed brands: before authoring a copy of another maker's product, check whether the maker has an active Specsket company that already published it (`specsket_search_products` with `vendor_ids`). A published product can be linked into the distributor's storefront through the vendor-authoring link flow instead of being copied; keep a copy, with brand and manufacturer evidence, only when the maker has no company or no published product.

Classification and images:
- `product_types` accepts only the system types `Material` (building products) and `FF&E` (furniture, fixtures and equipment). Put the supplier or category label in `product_subtypes`. If the type is genuinely unclear, leave `product_types` out and say why.
- An image URL that returns HTTP 200 and an image Content-Type is not enough evidence. Prefer URLs whose bytes you could confirm are really an image; Specsket rejects unknown bytes, HTML and SVG. Do not use a URL you saw only as a page or thumbnail.

Troubleshooting:
- Chunk persistence timeout (57014): abandon the job and start a new scope with smaller partitions; never send a different payload under the old key.
- Receipts last about ten minutes. A validation receipt that is older or has under 120 s left: re-validate the unchanged payload. An expired execution receipt: call `specsket_refresh_product_ingestion_execution_receipt` with the execution id.
- `issues[].expected` holds the correct value for a wrong supplied value; copy it, or omit the field. Duplicate or unknown `key:` errors name the key.

When `specsket_get_ingestion_candidate_summary` is listed, call it for each accepted `domain_record_id` after staging and report any count lower than the source (zero installation or document counts mean nothing was saved under the native roots it checks, not that the source had none). It cannot approve or publish.

Before calling any batch complete, reconcile source data to actual saved product fields: primary and gallery images, exact variant identities and supported-axis tuples, technical groups, instructions, documents and applicability, and every source-backed field in the live catalog. State unavailable or unresolved values with evidence and reasons instead of inventing them. Source JSON, accepted record counts and successful saves are not proof of imported images, native variants or transferred files. Inspect a saved representative candidate for every vendor and page shape before continuing a batch, then verify every record's source-to-saved counts; if it lacks source-backed fields, fix the mapping first.

Validating a chunk, including a request to validate or preview without staging, needs a private draft scope and execution, created by writes (scope upload, finalize, open the execution) that stage nothing, create no product and are visible to no one else; an unused draft stays in the account (it cannot be discarded yet), so never say it disappears. Confirm once, in plain words, before the scope upload ("To validate I need to create a private draft in <the vendor's or your> account. Nothing is staged and no product is created. Go ahead?"): that one confirmation covers the scope upload, finalizing and opening the execution, and nothing after them. The same yes covers re-creating the draft for the same product in this conversation. After the user's yes to the plan or structure, create the draft and validate without asking again; job creation, approval and link creation keep their own confirmations. Staging keeps its own separate confirmation. "Do not stage or submit" does not forbid the draft and is not consent either. If the user declines, stop at the field preview and label it "not validated by Specsket".

Before calling a write tool, summarize the exact records and effects of that single phase and obtain the separate explicit confirmation that workflow contract step 8 requires for each write phase (the private draft is one phase; `specsket_stage_validated_chunk` is one phase: one confirmation naming the job and the staging of its records into review, or pass `dispatch: false` to confirm the staging separately). For a vendor principal, name the target vendor. For a designer principal, state that the records enter that designer's private review queue and cannot be assigned to a vendor. For a project-aware designer job, also show the exact project, selected rooms, context revision, fit classifications, and that approval means **Approve to My Library** only. For a platform admin, state that OAuth remains platform-scoped and does not create a vendor, user, store, or membership.

After confirmation, create the job, stage the exact validated records, inspect every `record_results` entry (workflow contract step 11), and complete the job. Then follow workflow contract step 13: call `specsket_create_review_session` with the completed `job_id` and, as `candidate_id`, the domain_record_id of the first accepted record the user should review, print the permanent `review_url` and an **Open signed-in Specsket review** link from `browser_launch_url` with its expiry (explain the 60-second signed-in link and obtain a separate confirmation before link creation; create another only when the user asks), and ask the host to open it in the visible in-app browser when available. Never put the browser ticket anywhere else or claim it is permanent.

Never call supplier onboarding tools for a product error. Never publish, approve, directly mutate product tables, or claim an import succeeded before job completion returns a review URL.
