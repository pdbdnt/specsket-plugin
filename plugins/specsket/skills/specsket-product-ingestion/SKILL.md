# Specsket product ingestion

Use this skill only for the `product_ingestion` workflow and `product` entity.

Use the strict validated product workflow by default for imports, including requests to extract deeply, populate product fields, include variants, or stage complete products. The user does not need to say “strict.” Recovery availability is not a reason to downgrade those requests. Use the [recovery capture contract](../../references/product-recovery-capture-contract.md) only when the user explicitly requests incomplete review drafts and its three operations are advertised. For that path only, its preparation/confirmation/staging procedure replaces the strict write sequence below. Research, exact evidence, truthful completeness, destination authorization, and separate human approval remain mandatory. Never strip an existing governed envelope or switch paths to evade authorization, project-assessment, checksum, digest, or receipt failures. Preserve existing signed captures and successful candidates; corrections must not silently duplicate products.

## What to read, and when

Each step below starts with the references to read before it; read each when its step starts, not all up front. Every rule in them is as binding as this skill. Read a reference section only when its situation applies:
- the matching file listed in [rules for specific situations](../../references/ingestion-conditional-rules.md): an older Specsket without `product_discovery_scope_contract`, a host that computes canonical digests, a platform-admin principal (destinations, resolved before validation, and missing vendor organizations), project-aware designer research, an original refused before native writes or whose permission expired, no live Specsket connection, or no authoring kit;
- a numbered step of the workflow contract's "Visible source review" when this skill or a reference names it (for example "workflow contract step 10"): those steps are the general Specsket workflow, and the strict sequence below carries them for product ingestion;
- [the installation and download field rules](../../references/evidence-installation-downloads.md) when you write installation entries or downloads;
- [staging recovery](../../references/staging-recovery.md) ("When the 502 is the app, not the MCP", "Untouched original permission renewal", "Known pre-native no-effect disposition", "Canonical zero-stage closure"), and the evidence contract's "Original operation outcome evidence", when that outcome occurs;
- [the field catalog contract](../../references/field-catalog-contract.md) when the user asks which Specsket fields exist or you need the `field_catalog` shape to lay out the preview.

## Strict sequence at a glance

This is the whole write path. Never compute or type an id or digest that Specsket can derive (even when your host can run code). When the host saves a large result to a file, read only the parts you need from that file. You author content and natural keys; Specsket derives ids and digests and returns them. Copy values only from responses.

0. Read first: [the visible source review](../../references/visible-source-review.md) (the browser pass) and the "Large responses" note in [ingestion staging gotchas](../../references/ingestion-gotchas-staging.md). Authoring kit. When `specsket_get_product_authoring_kit` is listed, read it in parts: `part: core` carries the principal and workflow gates, the current entity fields and submission contract and `authoring_shapes` (the ingestion contract blocks, including `product_discovery_scope_contract` and the planning limits, are in `specsket_get_capabilities`, which you read first; an older server still repeats them in core); `part: scope` carries the discovery-scope schemas (read it before uploading the scope, and read `part: presentation` as well before resolving a `$ref` in it, because a current server no longer repeats the shared schemas); `part: presentation` carries the current wrapper with its presentation, applicability, coverage and readiness schemas (read it before writing `product_presentation` and its sidecars). `part: legacy` is only for an older flow or a job made by hand (`applicability_job_create`). Otherwise call `specsket_get_capabilities`, then read the `current` entity schema (with presentation contracts when advertised) and the research contract. The derived flow needs `product_discovery_scope_contract.server_derivation`, `product_discovery_scope_contract.chunk_digest_derivation` and `product_discovery_scope_contract.chunk_id_derivation` all true. If any is absent (older Specsket), ids and digests must be supplied by the client: stop and tell the user rather than guess hashes you cannot compute. Use taxonomy search for functional categories and CSI, never freehand IDs. Reuse the research contract, when you read it, while its digest and the connected principal are unchanged.
1. Read first, before the first field preview: [the extraction and authoring rules](../../references/ingestion-authoring-rules.md) in full, [the ingestion preview contract](../../references/ingestion-preview-contract.md), [the evidence contract](../../references/evidence-contract.md), [rendered-page extraction](../../references/rendered-page-extraction.md), and, when capabilities advertise `product-readiness@1`, [the product readiness contract](../../references/product-readiness-contract.md). Source inventory from rendered pages and every linked official document; account for every active catalog field (ingestion preview contract: "Field coverage and source documents"). Before the first field preview, ask the user whether they want the full field list (the default) or only the filled and unresolved fields, and follow the answer ([preview layout](../../references/ingestion-preview-contract.md#preview-layout)); with no answer or no user present, show the full list.
2. Read first: [ingestion scope gotchas](../../references/ingestion-gotchas-scope.md) and [the discovery-scope evidence rules](../../references/evidence-discovery-scope.md). Scope. Choose a parent-topology scope (`bounded` prefix or `all_discovered`) in ONE fragment. Upload the fragment with natural keys only: `key` on source parents and orderable variants, `key:<k>` references to them inside the same fragment, and inline `evidence` / `source` objects on evidence bindings. When `specsket_upload_product_discovery_scope_fragment_from_file` is listed, write the upload (`scope_id`, `revision`, `header`, `capability_digest`, `fragment`) to a file in the payload folder and upload it from there: never print the file back to send it inline. Its answer carries only the ids you copy later (`server_derived.source_parents` with their orderable variants by key, and `execution_partitions`); the full answer is in `result_file`. Omit every derivable id and digest (including `authority_key` and `source_parent_id` on source parents, `orderable_variant_id`, `partition_digest` and a partition's `evidence_refs`: a hand-computed value that differs fails the upload), but keep the authored `evidence_ref` and `source_id` on each evidence binding. Upload with `capability_digest` copied from capabilities `product_ingestion_planning_limits.digest`. Finalize with the `scope_id` and `open_execution: { idempotency_key }` (your own key) when the finalize tool lists it: one call, one confirmation, and the response carries `execution` (its `id` and `execution_receipt`) instead of a scope receipt. Otherwise finalize with the header only (or the `scope_id`) and create the execution with `scope_id`, `scope_root_digest` and `scope_receipt` (both from the finalize response; the digest is `scope.root_digest`), the same `capability_digest`, your own idempotency key, and `partitions`/`assignments` omitted. Use an absolute, stable `checkpoint_ref` per partition. The execution response returns NO partitions: take `id` (the execution id) and `execution_receipt` from it, and `partition_id` and `partition_digest` from the upload response `server_derived.execution_partitions` entry whose `partition_id` matches. Every source in a chunk must be bound by a partition evidence binding of the scope, and any inline `evidence`/`source` object the chunk repeats must be identical to the one in the scope fragment; otherwise job creation fails with a 409, and since fragments are immutable the scope must be re-created. Size partitions at 1-2 heavy products up front.
3. Read first: [ingestion validation gotchas](../../references/ingestion-validation-gotchas.md); copy its "Copy these shapes" entries (never write them from memory) and answer its "Quality gate". Per chunk (one partition = one job = one chunk, 1-2 heavy products), author `product@3`, presentation, applicability, `product-source-coverage@2` and readiness. Give every presentation object an `external_key`, reference objects in the same record as `key:<external_key>`, and omit ids, generated SKUs, group/occurrence ids and every digest. For combination and selector images give only the URLs with `evidence_refs` (validation gotchas, "Combination and selector images"). When capabilities advertise `chunk_scope_evidence_reuse`, leave out of `evidence_catalog` and `sources` every entry you already uploaded inline with the scope: the server adds them (`derived.values.evidence_from_scope`); supply only evidence the scope does not bind. Never reuse a key for a different thing; renaming an `external_key` changes every id derived from it, so a retry with a renamed key is a different record. An applicability occurrence's `native_pointer` follows the validation gotchas' pointer rule. When capabilities advertise `chunk_write_once`, write each fact once (kit `authoring_shapes`: `download_written_once`, `spec_table_applicability`, `per_combination_table`). Give a download `write_once_applies_to` and leave out its applicability occurrence and, when the file is available and not a certificate, its `document_coverage` entry. Set `derive_technical_group_occurrences: true` on the applicability record and leave out its technical-group occurrences. Write a table that repeats per finish as one `per_combination` table. With `chunk_write_once_2`, also write each page URL once (`page_urls` on the submission, then `page:<key>`), give a table's shared row evidence once (`row_evidence_refs`), and leave out coverage counts, `local_summary`, configurable selector axes and, with readiness, `media.images` (kit `written_once_more`). Otherwise, applicability occurrences for technical groups (and other presentation groups) need an authored `source_locator_key`: any stable string unique per occurrence within the record (e.g. `grp-<external_key>`); it feeds the derived occurrence id, so keep it identical on retries and never reuse it for another occurrence. In `product-source-coverage@2` copy `discovery_scope_digest` (finalize `scope.root_digest`), `execution_id` (the execution response `id`), `execution_partition_id` and `execution_partition_digest` (matching upload `server_derived.execution_partitions` entry); you still author `completeness_scope` and `completion_status`, and the counts unless `chunk_write_once_2` lets you leave them out. When any download uses `write_once_applies_to`, leave `document_coverage.detected_count` out: it includes the coverage entries the server builds for those downloads, which you do not see. `key:` references are NOT resolved in chunk sidecars: coverage `source_parent_id` and `orderable_variant_ids`, and readiness `grouping.source_parent_id` and `represented_orderable_variant_id`, must be the real `sp:`/`ov:` ids copied from the scope upload response `server_derived.source_parents[]` (`source_parent_id`, and each `orderable_variants[].orderable_variant_id`), matched by the `key` you gave that parent/variant.
4. Validate the chunk. When `specsket_validate_records_from_file` is listed, write the chunk to a file in the payload folder and validate it from there: the chunk never enters your context, the answer is a short summary with the first issues (`issues_preview`) and `chunk_cache.handle`, and the full answer is saved to `result_file` (read it only for issues beyond the preview). Correct the file and validate it again. Without that tool, validate inline; when the answer carries `chunk_cache.handle`, send corrections as `base_chunk` plus `patch` and stage with `chunk_handle` rather than resending the chunk (staging gotchas). Write observations, trace entries, relationships and profiles to the kit's `authoring_shapes` schemas (exact validators: no extra keys, only the listed enum words; leave out the `server_fills` keys). Passing validation does not mean the listing is complete. Copy from the response: the signed receipt, `job_binding` (`topology_manifest`, per-record digest maps, `product_structure_digest`, `record_manifest_digest`, the suggested `job` block), `request_digest` and `derived.values` (the answer is compact by default; validate with `verbose: true` only when you need the normalized records or the full key-to-id map). `job_binding` is complete only when `single_chunk` is true; if false, stop and tell the user (multi-chunk jobs cannot be built plugin-only). Plugin-only agents do not call `specsket_plan_product_ingestion_jobs`; the digest comes from `job_binding`. Read `derived.values` (including `repaired` and `profile_lists_extended`) before staging; from a file, the answer's `derived_preview` shows them, so read `result_file` only when it says more were repaired than it lists: if the server filled or changed a value you did not intend, such as a unit added to a profile or a replaced `normalized_context`, fix the source of the mistake and validate again.
5. Read first: the rest of [ingestion staging gotchas](../../references/ingestion-gotchas-staging.md) and, when capabilities report `product_chunk_stage_intent.enabled`, [durable original chunk staging](../../references/durable-chunk-staging.md). When `specsket_stage_validated_chunk` is listed and `job_binding.single_chunk` is true, steps 5 and 6 are one call (one confirmation for job creation and staging): pass the validate answer's `chunk_cache.handle`, the `execution_receipt`, and your own `job_idempotency_key`, `operation_id` and `chunk_idempotency_key` (write them down first; a retry repeats the identical call, including the same `execution_receipt`, and resumes the saved job and intent). It creates the job, prepares the stage intent and dispatches; if dispatch is refused (for example storage not yet enrolled by the owner) the prepared intent is kept and you dispatch it later with `specsket_dispatch_product_chunk_stage_intent`; an `unknown` outcome is reconciled first, never re-sent. When capabilities report `product_chunk_stage_intent.enabled` false (the hosted Specsket service), the same call stages through the records route instead and answers `route: records`: there is no intent and no separate dispatch, the staged chunk goes straight to review, `operation_id` is unused, and `dispatch: false` creates the job only. Its `unknown` outcome is reconciled with `specsket_get_ingestion_job` first; a retry repeats the identical call with the same keys, never a new key. After `execution_receipt_expires_at` the call cannot recreate the job, so stage that `job_id` with `specsket_stage_validated_records` and the same chunk idempotency key instead (a chunk already saved under the key is returned, not staged twice). Otherwise, create the job (schema: kit `part: legacy`, `applicability_job_create`) with `job_binding.job` and `job_binding.topology_manifest`, plus: `schema_version` and `taxonomy_versions` from your own submission (leave out `source_manifest`: with `execution_binding` the server takes exactly the partition's sources from the scope; supply it only when the server answers that it is required, as your submission's `sources`); your own idempotency key; and `execution_binding` = `execution_id` (the execution response `id`), `execution_partition_id`, `execution_partition_digest`, `discovery_scope_digest`, `execution_receipt` (values from step 2). `request_digest` and the manifest digests may be omitted. Create the job and stage within the execution receipt's life (about ten minutes, see `execution_receipt_expires_at`).
6. Stage with the job id (when capabilities report `product_chunk_stage_intent.enabled`, stage through `specsket_prepare_product_chunk_stage_intent` then `specsket_dispatch_product_chunk_stage_intent` per the workflow contract, not `specsket_stage_validated_records`), `chunk_index`, your own chunk idempotency key, the identical authored payload and the validation receipt. `content_digest` is optional (it equals validation's `request_digest`). Any change to the payload needs a new validation.
7. A timeout, 502, 120 s tool cutoff or lost response is not a failed write (read the workflow contract's paragraph on an uncertain product chunk stage, after its numbered steps). Call `specsket_reconcile_product_ingestion_chunk` with the same job, chunk index and idempotency key before anything else, then wait and reconcile again while it stays unknown; never stage again with a new key or a different payload for the same chunk.
8. Complete the job with `complete_execution_id` (the execution id) to close the execution in the same call (one confirmation; the execution closes only when all its partition jobs are complete, otherwise the answer says so), or complete the job and then the execution. When capabilities report `product_ingestion_completion_intent.enabled` and its three tools are callable, complete the job without `complete_execution_id`, then complete the execution through workflow contract step 12. Read step 12 too before reporting execution status after a reconnect or a completion response (`specsket_get_product_ingestion_execution` progress; unknown counts stay unknown). Print the permanent review URL.

Plugin-only limits (say them to the user when they bite): a multi-fragment scope needs `header.total_canonical_bytes` up front, which you cannot compute, so keep the scope to one fragment; `exact_identity_subset` needs client-supplied `ov:` identity keys, so it is not available plugin-only; `source.content_sha256` of external bytes is not derivable, so omit it unless the host exposes the bytes. Classification and applicability outcomes, coverage counts and readiness bindings stay your judgement from evidence and are never defaulted to `all_variants`. Plugin users should omit derivable values rather than supply them; a wrong supplied value is rejected (with `issues[].expected`) only on paths where the server can derive it.

Chunk size: Specsket cancels a chunk write that runs too long and the advertised record cap is only a schema limit, so do not fill chunks to it.

Distributed brands: before authoring a copy of another maker's product, check whether the maker has an active Specsket company that already published it (`specsket_search_products` with `vendor_ids`). A published product can be linked into the distributor's storefront through the vendor-authoring link flow (for a company connection that offers it) instead of being copied; keep a copy, with brand and manufacturer evidence, only when the maker has no company or no published product.

Classification and images (learned in live runs):
- `product_types` accepts only the system types `Material` (building products) and `FF&E` (furniture, fixtures and equipment). Put the supplier or category label ("Raised access floor", "Crash cushion") in `product_subtypes`. Validation reports `product_types_not_system_type` for a record or profile that breaks this; an approved candidate cannot carry a supplier label. If the type is genuinely unclear, leave `product_types` out and say why.
- An image URL that returns HTTP 200 and an image Content-Type is not enough evidence. Prefer URLs whose bytes you could confirm are really an image. Specsket accepts a valid image whose declared type differs from its bytes (for example a JPEG served as `image/webp`) and only counts it in telemetry, but it still rejects unknown bytes, HTML and SVG. Do not use a URL you saw only as a page or thumbnail.
- If a dispatch response carries `last_attempt` (a code such as `integration_image_invalid_image` and `issue_codes`), the stage attempt failed and the original is still unresolved: read the original intent and job and reconcile; fix the named problem (for example replace the image) in a fresh attempt only when the original is proven uncommitted. `last_attempt` is a diagnostic, never proof of non-commitment.

Troubleshooting:
- Chunk persistence timeout (57014): abandon the job and start a new scope with smaller partitions (1-2 heavy products each); one partition = one job = one chunk, and never send a different payload under the old key.
- Receipts last about ten minutes, so author the payload and dispatch in the same hour. A validation receipt that is older or has under 120 s left: re-validate the unchanged payload. An expired execution receipt: call `specsket_refresh_product_ingestion_execution_receipt` with the execution id. A prepared intent that waited longer can have its permission renewal denied (`chunk_permission_renewal_denied`, not retryable); then start a fresh scope, execution and job instead of retrying.
- `issues[].expected` holds the correct value for a wrong supplied id or digest; follow-on errors are suppressed only for the `content_digest`/`occurrence_id` paths that could not be derived, other real errors can still be listed. Copy `expected`, or simply omit the field.
- Duplicate or unknown `key:` errors name the key: keys must be unique per kind within a record, and a `key:` reference must name an `external_key` in the same record.

When `specsket_get_ingestion_candidate_summary` is listed, call it for each accepted `domain_record_id` after staging: it returns a URL-free summary of the staged candidate (name, brand, manufacturer, classification labels, and counts of images, documents, variants, technical properties and installation entries) so you can compare saved against source without the admin UI. Report any count that is lower than the source; zero counts for installation or documents mean nothing was saved under the native roots it checks, not that the source had none. It cannot approve or publish.

Before calling any batch complete, reconcile source data to actual saved product fields. Check primary/gallery images, exact documented variant identities and supported-axis tuples, technical groups, instructions, documents and applicability, and every source-backed field in the live catalog. State unavailable or unresolved values with evidence and reasons instead of inventing them. Source JSON, retained arrays, local downloads, accepted record counts, and successful saves are not proof of imported images, native variants, or transferred files. Inspect a saved representative candidate for every vendor and page shape before continuing a batch; then verify every record's source-to-saved counts. If the representative lacks source-backed fields, fix the mapping and verify it before continuing.

Before calling a write tool, summarize the exact records and effects of that single phase and obtain the separate explicit confirmation that workflow contract step 8 requires for each write phase (finalizing with `open_execution` is one phase: one confirmation that names both the frozen scope and the opened execution; `specsket_stage_validated_chunk` is one phase: one confirmation that names the job and the staging of its records into review, or pass `dispatch: false` to confirm the staging separately, within the execution receipt's life). For a vendor principal, name the target vendor. For a designer principal, state that the records enter that designer's private review queue and cannot be assigned to a vendor. For a project-aware designer job, also show the exact project, selected rooms, context revision, fit classifications, and that approval means **Approve to My Library** only. For a platform admin, state that OAuth remains platform-scoped and does not create a vendor, user, store, or membership. After completion, explain the 60-second signed-in link and obtain a separate confirmation before link creation or browser opening. If the link expires, create another only when the user asks to open the completed review again.

After confirmation, create the job, stage the exact validated records, inspect every `record_results` entry (workflow contract step 11), and complete the job. Then follow workflow contract step 13: call `specsket_create_review_session` with the completed `job_id` and, as `candidate_id`, the domain_record_id of the first accepted record the user should review, print the permanent `review_url` and an **Open signed-in Specsket review** link from `browser_launch_url` with its expiry, and ask the host to open it in the visible in-app browser when available. Never put the browser ticket anywhere else or claim it is permanent.

Never call supplier onboarding tools for a product error. Never publish, approve, directly mutate product tables, or claim an import succeeded before job completion returns a review URL.
