# Rendered-page extraction

Part of [the workflow contract](workflow-contract.md); every rule there applies.

Product pages are frequently assembled in the browser: variant and colour selectors, size or finish configurators, accordions, tabs, modals, lazy-loaded galleries and download panels. A static HTTP fetch (curl, a text-only web fetch, a model-summarised page, saved `view-source` HTML) can silently miss them, so it is never sufficient evidence of absence.

- Load every product-detail page in a real rendering browser. When the visible in-app browser is available, use it (it is also [the visible source review](visible-source-review.md)). Otherwise use headless or headed Chromium (for example Playwright). If neither is available, say so, do not claim the page was fully extracted, and limit the output to what the static source supports with the gap recorded. Use a desktop viewport of at least 1440 px wide, wait for network idle (or, when analytics keep the network busy, the load event plus a settle delay of about five seconds), scroll the full page to trigger lazy content, then expand every accordion, tab, modal and selector that can change the product's variants, images, specifications, documents or certifications.
- When an official page of a product the user asked to ingest cannot be read at all, so that the static fetch gives no usable product content (an HTTP 403 or other refusal, a login wall, or content that only appears through JavaScript with no rendering browser available), tell the user plainly which page was blocked and how, and ask for one of: a rendered browser pass they allow, or the page content and the document files pasted or attached. Never switch to another manufacturer or product on your own, and never replace the blocked official source with unofficial or remembered values; official documents found elsewhere (for example the maker's own PDF on a content delivery network) still count, cited as their own sources. Record the blocked page in `technical.analysis_trace` with `source_type: manufacturer_product_page`, its source id, outcome `blocked` and the refusal as the note. In product discovery, mark that candidate blocked with its reason instead; other candidates remain allowed.
- Extract from the rendered DOM. Keep the raw response hash with the other source evidence, and note the render method, viewport, load time and interactions performed in the extraction notes or checkpoint metadata that the live schema provides; do not invent new record fields for them.
- When a field, image, variant list or document appears absent in a static fetch, re-check it in the rendered page before recording `not_found`. When the rendered page also lacks it, record that the rendered page was checked.
- Walk each selector. Every selectable colour, size or finish that publishes its own identifier, image or document is a documented variant; capture its identifier, image and per-variant facts as you select it. Do not conclude that a product has no variants from the default state alone. For configurators whose combinations are not individually published, walk only the documented combinations and the axes Specsket supports; never enumerate a Cartesian product, and record the rest as not individually documented.
