# Ingestion validation: rules the schema does not show

Each rule below cost at least one failed call because neither the entity schema nor the error text named it. Read this before authoring a chunk (skill step 3). Rules for the scope are in [ingestion scope gotchas](ingestion-gotchas-scope.md); rules for staging and large responses in [ingestion staging gotchas](ingestion-gotchas-staging.md).

## Copy these shapes (do not invent field names or enum values)

Every entry below is accepted exactly as written. Change the values, keep the keys and enum words. The first two failed most often in isolated runs when written from memory.

`technical.properties.value[]` (observations; exact keys and enums under "Chunk"). `status` not `state`; `scope` is a plain word, not an object:
```json
{ "property_key": "edge_type", "status": "verified", "value": "RECTIFIED", "value_origin": "direct", "scope": "product", "evidence_refs": ["ev.page"] }
{ "property_key": "water_absorption", "status": "not_found", "scope": "product", "evidence_refs": ["ev.datasheet"], "checked_source_types": ["manufacturer_product_page", "technical_datasheet"], "note": "The datasheet publishes no value." }
```
`technical.analysis_trace.value[]` (exact keys under "Chunk"). `source_type` must be one of the profile's source types (the allowed words are listed under "Chunk"); a `not_found` or `blocked` outcome needs a `note`:
```json
{ "source_type": "technical_datasheet", "source_ids": ["src.datasheet"], "outcome": "not_found", "note": "No water absorption value is published." }
```
`compatible.relationships.value[]`. `relationship_type` is `accessory`, `product_set`, `recommended`, `related`, `similar`, `installation_materials` or `installation_tools` (not `compatible_with`); name the target by record key or SKU:
```json
{ "relationship_type": "installation_materials", "target_sku": "ADH-120" }
```
Two relationships with the same target and `relationship_type` that differ only in `related_variant_sku` are stored as one; to scope a relationship to some variants, use its applicability occurrence instead of a second entry.
`product_profile_catalog[]` (minimal; the server fills the rest from the record). Properties list the keys you will observe:
```json
{ "profile_key": "profile.insulation", "title": "Insulation board", "source_escalation": ["technical_datasheet"],
  "properties": [{ "key": "thermal_conductivity", "display_name": "Thermal conductivity", "value_type": "quantity", "criticality": "critical", "allowed_units": ["W/mK"] }] }
```
`technical.client_analysis_metadata.value` needs only `method_version` and `family_key` (equal to the profile's); the server fills the checkpoint pair and the outer `technical.properties.evidence_refs`, and reports what it filled in `derived.values`.

## Quality gate before you validate

Validation only proves the shape. In the first isolated runs a product passed validation with its specification table stored as one flat attribute object, its tolerance note left out, and every per-size datasheet marked "All variants". Answer each line below from the rendered page and every linked document before the first validate call, and again from the candidate summary before completing the job:

1. Rendered page ([rendered-page extraction](rendered-page-extraction.md)): a static fetch and the page's JSON feed miss footers, disclaimers and per-selector links. Without a rendering tool, treat every footer or note as unchecked in the report.
2. Specification tables. Each key/value table on the page (product type, code, size, series, colour, technology, typology, structure, surface look, edge, thickness, unit) becomes a presentation `technical_groups` entry with one row per line. Do not leave it only in `technical.attributes`. After staging, `parameter_groups` in the candidate summary must be above 0 when the page has such a table.
3. Notes and disclaimers. Tolerances ("+5% below 200 mm"), reference-only image statements and "specifications may change" notes go in `technical.specification_notes`, cited to the page or sheet that states them. If the only copy is a garbled PDF, quote the page text; if there is none, record the note as unresolved with the reason. Never drop it silently.
4. Documents. Each file that names a size or SKU in its title or URL (for example a product sheet "A06GICMR-WHE.N0X0P (60x60cm)") is scoped to that combination with a `download` occurrence; only files that really cover the whole family (a shared test-method datasheet) stay "All variants". An empty `product_variant_applicability` `occurrences` list is accepted and then shows every download, technical group and installation item as "All variants" in the review screen: check its Download tab against the source before calling the job complete.
5. Description. Use the page's own text. If the page has none, say "not found" with the sources checked.
5a. Units. Every size, length, thickness and weight carries the unit the source prints, in the value ("600x1200 mm") or its unit field. A bare "28x46" or "1500" is stored as "unit not stated" and never confirms a specification search. Do not guess a unit the source does not state.
   A current server also returns these checks as `severity: "warning"` issues on a successful validation. They do not block staging and are not part of the signed receipt, so a successful validation can carry issues: filter by `severity` and never read "0 issues" or an unfiltered `issues[]` count as the success signal. The local file-based validate tool reports `error_count`, `warning_count` and `warning_codes` for this reason. Treat each warning as a defect to fix, or say in the report why it does not apply.
6. After staging, read the candidate summary and compare it with this list. A zero where the page has content (groups, notes, description) is a defect to fix before `specsket_complete_ingestion_job`, not a result to report.

## Chunk (before `specsket_validate_records`)

- `technical.client_analysis_metadata` is required whenever `technical.profile_key` is used. The server fills it (method version, family key and the checkpoint pair) from the profile and strips keys it does not know, listing both in `derived.values`; if you write it, the value is `{ "method_version", "family_key", "checkpoint_version", "checkpoint_digest": "sha256:<64 hex>" }` plus an optional `phase_timings_ms`, with `family_key` and `method_version` equal to the profile's (`client_profile_metadata_mismatch` otherwise, with the right values in `expected`).
- Each item of `technical.properties` (an observation) is exactly: `property_key` and `status` (both required), and optionally `value`, `value_origin` (`direct`, `normalized` or `derived`), `unit`, `test_or_classification_system`, `scope` (a string: `product`, `series`, `manufacturer_platform` or `material_class`, not an object), `evidence_refs`, `checked_source_types`, `note`. `status` is one of `verified`, `not_found`, `insufficient_evidence`, `conflicting_evidence`, `not_applicable`, `requires_vendor_confirmation`. Only `verified` may carry `value`, `value_origin` or `derivation`. Other keys (`state`, `key`, `value_origin: source_stated`) are rejected.
- Each item of `technical.analysis_trace` is exactly: `source_type`, `source_ids` (at least one), `outcome` (`checked`, `not_found`, `blocked` or `not_applicable`) and an optional `note`. `source_type` is one of `manufacturer_product_page`, `technical_datasheet`, `technical_catalogue`, `declaration_of_performance`, `test_certificate`, `installation_guide`, `maintenance_guide`, `warranty_document`, `authoritative_supplier_page`, `vendor_confirmation`; a certifications page is `authoritative_supplier_page`. A current server reports each bad entry with its index and the failing key (`client_analysis_trace_invalid`); older servers say only that an entry is invalid.
- Applicability occurrences point at saved fields with JSON pointers into the saved draft, not dotted paths or paths into your request: a technical group is `/custom_parameter_groups/<n>` and a technical file is `/technical_files/<n>`. The other roots are `/technical_data_cards/<n>` (technical cards), `/documents/<n>`, `/installation/<n>` and `/product_relationships/<n>` (compatible products). A current server repairs a wrong root when the item index is right (for example `/technical_cards/0` becomes `/technical_data_cards/0`); otherwise `applicability_pointer_unresolvable` lists the expected pointers in `issues[].expected`; copy them.
- A technical-group applicability occurrence binds the presentation group: `applicability: { "kind": "presentation_group", "presentation_group_id": "key:<group external_key>" }`, not `all_variants`.
- Media owners and roles must agree: a project image uses `owner_kind: project` with `role: project`; only the primary and gallery images use `owner_kind: product`.
- `analysis_trace` needs an entry for every `source_escalation` source type the profile asks for. The server adds a test or classification system an observation names to the profile property's `test_or_classification_systems`.
- A combination-scoped download occurrence needs `sku_aliases` and `occurrence_id`, but you do not send them: omit both and the server derives them (generated `SRC-` SKUs and the `sva1:` id). A wrong supplied value is replaced by the derived one (for `occurrence_id` only when the supplied `content_digest` matches the native draft; otherwise the call fails with the expected value) and listed in `derived.values.repaired`; check that list. The same applies to `presentation_group_digest`, an omitted `checkpoint_version`/`checkpoint_digest` (or a single `checkpoint_ref`), the outer `technical.properties.evidence_refs` (exactly the union of the observations' lists; older servers reject a mismatch with `technical_property_outer_evidence_mismatch`) and a pointer with the right index but wrong root.
- A unit on an observation must be in the profile property's `allowed_units`; the server adds a missing one to the list.
- Combination and selector images (presentation @3): give only `image_urls` on the combination and `image_url` on the option value, each with its `evidence_refs`, and leave out `image_media_reference_ids`, `image_media_reference_id` and their `media_references` entries; the server creates them (same URL, order and owner) and reports `derived.values.synthesized_media_references`, but not for a combination or value with no `evidence_refs`. Still author `media_references` for the product-owned primary image and for project, part and drawing images.
- A selector state must reference an inventoried official URL: list each per-size or per-colour page, and every other page you cite as a `source_page_url` in document or certification coverage, in `additional_official_urls`.
- Leave `source_coverage.local_summary` out (it counts selector states only, never documents; the server computes it and corrects a wrong value).
- `variant_matrix.option_types[].position` starts at 1 and is contiguous.
- An available, non-certificate download written once (`write_once_applies_to`) has no entry of yours in `source_coverage` `document_coverage.occurrences`: the server builds it, and writing it too fails with `download_coverage_written_twice`. Keep the `document_coverage` block with `"occurrences": []` (and no `detected_count`) when every download is written once. Do not use `write_once_applies_to` for an unavailable file or a certificate: write those downloads and their coverage entries in full.
- In `media_references` you write yourself, `owner_id` depends on `owner_kind`: for `product` (the primary and gallery images), `project` and `technical_drawing` it is the record's own `external_record_id`, written out (a `key:` reference is rejected); for `option_value`, `combination` or `wireframe` it is `key:<external_key>` of that value or combination (a wireframe is owned by its combination); for `part` it is `key:<external_key>` of that part.
- In `product_readiness.records[].primary_image`, leave `media_reference_id` out: the server fills it from the record's one product-owned primary media reference (and reports it in `derived.values.readiness_primary_image`). To name it yourself write `key:<external_key>` of that media reference. Never write an `sp1:media:` id: you cannot compute it, and a wrong one is refused.
- Every id in `product_readiness.records[].primary_image.ownership_evidence_refs` must also be listed in the `evidence_refs` of that record's product-owned primary media reference (the one `role: primary` entry of `media_references`); otherwise validate fails with `PRIMARY_IMAGE_EVIDENCE_REQUIRED`. Give both the same evidence ids, the ones that show the image belongs to this product.
- `product_readiness.records[].grouping.display_name` must equal that record's `information.name` exactly (same string, same spelling and case); otherwise validate fails with `PRODUCT_NAME_PROVENANCE_REQUIRED`. Write the name once and copy it to both places.
- `image_resolution` of a combination is filled by the server when it has its own `image_urls`, when its selected primary option value has an `image_url`, when it says `allow_parent_fallback: true`, and for a one-SKU product with a primary image; otherwise the error offers the choices. For `unresolved`, add one `product_structure.unresolved_nodes` entry: `node_id` is the combination's `external_key` written plainly (no `key:` prefix; `sku.<sku>` also matches), with a `reason` and `evidence_refs`, and give the combination no `image_urls` and no `allow_parent_fallback`.
- A combination SKU: when the source has a manufacturer SKU write `sku_origin: "manufacturer"` and the `sku`. When it has none, write `sku_origin: "generated_from_source_identity"` with the typed `source_identity` and leave `sku` OUT: the server derives the internal `SRC-` value (a SKU you invent fails with the expected value in the error).
- A `verified` technical property or quantity takes a number: the server converts an exact decimal, a grouped number or a fraction written as text (2-1/8 becomes 2.125) and lists it in `derived.values.repaired`; ranges, text and units inside the value stay errors, and the `unit` goes in `unit`. A failure is headed `validation_schema_invalid`: read every entry of `issues[]` (`issues_preview` or `result_file`).
- Give the `unit` with every measured value (weight, dimension, capacity, rating). A value without one passes with a `value_without_unit` warning that is still a defect; fix it before staging.
- On a large variant matrix one mistake repeats on every combination (dozens of invalid fields with one or two causes): generate all combinations from a single template and validate two or three first.
- A record with a presentation variant matrix needs `source_coverage.records[].selector_coverage.mode: configurable` (leave `axes` and `inspected_states` out and state the one official page you inspected as `selector_coverage.inspected_page`: the server writes one state per enabled combination from the matrix; list the states yourself only when the pages differ). The one exception is a true single SKU (exactly one combination and one value per option type): it may say `non_configurable` with `axes: []` and one inspected state with `selections: {}`. An `unresolved_states` entry may name only the axes it could determine (even none).
- Every `product@3` submission needs a `product_profile_catalog`, a `technical.profile_key` on each record and the matching `technical.client_analysis_metadata`. You write the profile minimally (see "Copy these shapes"): a current server fills `family_key`, `method_version`, `family_description`, each property's `description` and `reason`, the profile's `normalized_context` (taken from the record's classification, replacing a wrong one), the record's `technical.client_analysis_metadata`, and the `technical.profile_key` when the catalog holds one profile. Each replacement is listed in `derived.values`.
- On a configurable record (several variants) a compliance or certification claim that has no download cannot be `product-specific`: bind it to a combination-scoped download occurrence, use the scope the evidence supports, or record it as a technical property. In `certification_coverage` a `product-specific` entry on a configurable record needs an `applicability_occurrence_id` naming a normalized combination-scoped download occurrence that shares at least one evidence id with it (the server fills it when exactly one fits and names the candidates otherwise); when its file applies to the whole family, classify it `family-level` instead.
- The file-based tools: validate accepts a request file without `job_id`; the job needs the validation's `job_binding`, so validate once without it, create the job, then add `job_id` and the chunk `idempotency_key` to the file and validate again (same request digest) before preparing the stage intent from the file. These tools exist only on a local MCP and read files only from the folder configured on the MCP host, not from your working directory; a hosted, remote or plugin-only client sends `specsket_validate_records` with the payload inline and uses the chunk handle (staging gotchas).
- A platform administrator's validation also needs the routing manifest: `submission.record_manifest`, an array of `{ "external_record_id": "<id>", "routing": { "destination": { "mode": "vendor", "vendor_id": "<uuid>" } } }`, one per record; omit its digest (a vendor or designer connection gets its own manifest from the server).
- Validation checks request-level shape first. A stripped-down probe returns only top-level errors, so send the real payload and read every `issues[]` entry before fixing one.
- Receipts (validation, execution, scope) are long signed strings. Never retype or retype-from-memory a receipt: one wrong character gives a generic `product_execution_receipt_stale`. Save each response to a file and read the value from it programmatically.
- Two compatible relationships with the same source, target and type but different `related_variant_sku` are one relationship, so validate fails with `applicability_materialization_failed` and an `expected` hint. Keep one `related_variant_sku` per relationship or split them into separate items; variant-specific siblings of one target and type are not supported yet. An empty variant SKU next to a set one is fine.
