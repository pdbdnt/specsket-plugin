# Ingestion validation: rules the schema does not show

Found by running the plugin from an empty folder against the local MCP (26 Oct 2026). Each rule below cost at least one failed call because neither the entity schema nor the error text named it. Read this before validating a chunk; the scope and staging rules are in their own files, linked where they were.

## Copy these shapes (do not invent field names or enum values)

Every entry below is accepted exactly as written. Change the values, keep the keys and enum words. The first two failed most often in isolated runs when written from memory.

`technical.properties.value[]` (observations). `status` not `state`; `value_origin` is `direct`, `normalized` or `derived`; `scope` is a plain word (`product`, `series`, `manufacturer_platform`, `material_class`), not an object:
```json
{ "property_key": "edge_type", "status": "verified", "value": "RECTIFIED", "value_origin": "direct", "scope": "product", "evidence_refs": ["ev.page"] }
{ "property_key": "water_absorption", "status": "not_found", "scope": "product", "evidence_refs": ["ev.datasheet"], "checked_source_types": ["manufacturer_product_page", "technical_datasheet"], "note": "The datasheet publishes no value." }
```
`technical.analysis_trace.value[]`. `source_type` must be one of the profile's source types (for example `manufacturer_product_page`, `technical_datasheet`, `technical_catalogue`, `declaration_of_performance`, `test_certificate`, `installation_guide`, `maintenance_guide`); a `not_found` or `blocked` outcome needs a `note`:
```json
{ "source_type": "technical_datasheet", "source_ids": ["src.datasheet"], "outcome": "not_found", "note": "No water absorption value is published." }
```
`compatible.relationships.value[]`. `relationship_type` is `accessory`, `product_set`, `recommended`, `related`, `similar`, `installation_materials` or `installation_tools` (not `compatible_with`); name the target by record key or SKU:
```json
{ "relationship_type": "installation_materials", "target_sku": "ADH-120" }
```
Two relationships with the same target and `relationship_type` that differ only in `related_variant_sku` are stored as one; to scope a relationship to some variants, use its applicability occurrence instead of a second entry.
`product_profile_catalog[]` (minimal; the server fills the rest from the record). Properties list the keys you will observe:
```json
{ "profile_key": "profile.insulation", "title": "Insulation board", "source_escalation": ["technical_datasheet"],
  "properties": [{ "key": "thermal_conductivity", "display_name": "Thermal conductivity", "value_type": "quantity", "criticality": "critical", "allowed_units": ["W/mK"] }] }
```
`technical.client_analysis_metadata.value` needs only `method_version` and `family_key` (equal to the profile's); the server fills the checkpoint pair and the outer `technical.properties.evidence_refs`, and reports what it filled in `derived.values`.

## Quality gate before you validate

Validation only proves the shape. In the first isolated runs a product passed validation with its specification table stored as one flat attribute object, its tolerance note left out, and every per-size datasheet marked "All variants". Answer each line below from the rendered page and every linked document before the first validate call, and again from the candidate summary before completing the job:

1. Rendered page. Open the page in a browser or render it; a static fetch and the page's JSON feed miss footers, disclaimers and per-selector links. If no rendering tool is available, say so in the report and treat every footer or note as unchecked.
2. Specification tables. Each key/value table on the page (product type, code, size, series, colour, technology, typology, structure, surface look, edge, thickness, unit) becomes a presentation `technical_groups` entry with one row per line. Do not leave it only in `technical.attributes`. After staging, `parameter_groups` in the candidate summary must be above 0 when the page has such a table.
3. Notes and disclaimers. Tolerances ("+5% below 200 mm"), reference-only image statements and "specifications may change" notes go in `technical.specification_notes`, cited to the page or sheet that states them. If the only copy is a garbled PDF, quote the page text; if there is none, record the note as unresolved with the reason. Never drop it silently.
4. Documents. Each file that names a size or SKU in its title or URL is scoped to that combination with a `download` occurrence; only family-wide files stay "All variants".
5. Description. Use the page's own text. If the page has none, say "not found" with the sources checked.
5a. Units. Every size, length, thickness and weight carries the unit the source prints, in the value ("600x1200 mm") or its unit field. A bare "28x46" or "1500" is stored as "unit not stated" and never confirms a specification search. Do not guess a unit the source does not state.
   A current server also returns these checks as `severity: "warning"` issues on a successful validation (`description_missing`, `specification_table_not_in_groups`, `document_names_variant_but_scoped_to_all`, `value_without_unit`). They do not block staging and are not part of the signed receipt, so a successful validation can carry issues: filter by `severity` and never read "0 issues" or an unfiltered `issues[]` count as the success signal. The local file-based validate tool reports `error_count`, `warning_count` and `warning_codes` for this reason. Treat each warning as a defect to fix, or say in the report why it does not apply.
6. After staging, read the candidate summary and compare it with this list. A zero where the page has content (groups, notes, description) is a defect to fix before `specsket_complete_ingestion_job`, not a result to report.

## Chunk (before `specsket_validate_records`)

- `technical.client_analysis_metadata` is required whenever `technical.profile_key` is used. Its value is `{ "method_version": "<string>", "family_key": "<profile familyKey>", "checkpoint_version": "<string>", "checkpoint_digest": "sha256:<64 hex>" }` plus an optional `phase_timings_ms`; no other keys. `family_key` and `method_version` must equal the referenced profile's `familyKey` and `methodVersion` (`client_profile_metadata_mismatch` otherwise). On a current server the error names the missing key (`zodDetail`) and its `expected` holds the profile's `family_key` and `method_version`; older servers return a bare `Required` at `...client_analysis_metadata.value`, which means one of these four keys is missing.
- `checkpoint_digest` only has to be `sha256:` plus 64 hex characters; it is never compared with anything. Omit the pair (or send one `checkpoint_ref`) and a current server fills it and says so in `derived.values`.
- Each item of `technical.properties` (an observation) is exactly: `property_key` and `status` (both required), and optionally `value`, `value_origin` (`direct`, `normalized` or `derived`), `unit`, `test_or_classification_system`, `scope` (a string: `product`, `series`, `manufacturer_platform` or `material_class`, not an object), `evidence_refs`, `checked_source_types`, `note`. `status` is one of `verified`, `not_found`, `insufficient_evidence`, `conflicting_evidence`, `not_applicable`, `requires_vendor_confirmation`. Only `verified` may carry `value`, `value_origin` or `derivation`. Other keys (`state`, `key`, `value_origin: source_stated`) are rejected.
- Each item of `technical.analysis_trace` is exactly: `source_type`, `source_ids` (at least one), `outcome` (`checked`, `not_found`, `blocked` or `not_applicable`) and an optional `note`. `source_type` is one of `manufacturer_product_page`, `technical_datasheet`, `technical_catalogue`, `declaration_of_performance`, `test_certificate`, `installation_guide`, `maintenance_guide`, `warranty_document`, `authoritative_supplier_page`, `vendor_confirmation`; a certifications page is `authoritative_supplier_page`. A current server reports each bad entry with its index and the failing key (`client_analysis_trace_invalid`); older servers say only that an entry is invalid.
- Applicability occurrences point at saved fields with JSON pointers, not dotted paths: a technical group is `/custom_parameter_groups/<n>` and a technical file is `/technical_files/<n>`. The other roots are `/technical_data_cards/<n>` (technical cards), `/documents/<n>`, `/installation/<n>` and `/product_relationships/<n>` (compatible products). A current server repairs a wrong root when the item index is right (for example `/technical_cards/0` becomes `/technical_data_cards/0`); otherwise `applicability_pointer_unresolvable` lists the expected pointers in `issues[].expected`; copy them.
- A technical-group applicability occurrence binds the presentation group: `applicability: { "kind": "presentation_group", "presentation_group_id": "key:<group external_key>" }`, not `all_variants`.
- Media owners and roles must agree: a project image uses `owner_kind: project` with `role: project`; only the primary image uses `owner_kind: product`.
- `analysis_trace` needs an entry for every `source_escalation` source type the profile asks for, and a `not_found` or `blocked` entry needs a `note`. A current server adds a test or classification system named by an observation to the profile property's `test_or_classification_systems`; an older server rejects the observation until you list it.
- A combination-scoped download occurrence needs `sku_aliases` and `occurrence_id`, but you do not send them: omit both and the server derives them (generated `SRC-` SKUs and the `sva1:` id). A wrong supplied value is replaced by the derived one (for `occurrence_id` only when the supplied `content_digest` matches the native draft; otherwise the call fails with the expected value) and listed in `derived.values.repaired`; check that list. The same applies to `presentation_group_digest`, an omitted `checkpoint_version`/`checkpoint_digest` (or a single `checkpoint_ref`), the outer `technical.properties.evidence_refs` (the union of the observations' lists) and a pointer with the right index but wrong root.
- A unit on an observation must be in the profile property's `allowed_units`. A current server adds a missing unit to the list; an older server fails with `verified_property_invalid` ("The verified value cannot declare a unit when the profile property has no allowed units").
- Profile property fields use these enums: `applicability_scope` is `family` or `product_extension` (not `all_variants`); `criticality` is `critical`, `important` or `recommended` (not `required`).
- `primary_image_option_type_id` is required for presentation @2 and @3 even though the compact schema marks it optional. Use `key:<external_key>` of the option that carries the primary image.
- Combination and selector images (presentation @3): give only `image_urls` on the combination and `image_url` on the option value, each with its `evidence_refs`, and leave out `image_media_reference_ids`, `image_media_reference_id` and their `media_references` entries. A current server creates them (same URL, order and owner) and reports `derived.values.synthesized_media_references`. It does not create them when the combination or value has no `evidence_refs`. Still author `media_references` for the product-owned primary image and for project, part and drawing images. If you do write combination entries yourself, `image_media_reference_ids` must point at them in the same order as `image_urls`, one to one.
- A selector state must reference an inventoried official URL: list each per-size or per-colour page in `additional_official_urls`. List there too every other page you inspected and cite as a `source_page_url` in document or certification coverage (download area, certifications page, collection page); otherwise validation warns `product_coverage_page_not_inventoried`.
- In `product-source-coverage@2` the selection axis key for a selector equals the presentation option's `external_key` (for example `opt.size`, not `size`), and the inspected tuple must match the enabled presentation tuple.
- `variant_matrix.option_types[].position` starts at 1 and is contiguous.
- In `media_references` you write yourself, `owner_id` for an `option_value` or `combination` owner is `key:<external_key>` of that value or combination.
- Every `product@3` submission needs a `product_profile_catalog`, a `technical.profile_key` on each record and the matching `technical.client_analysis_metadata`. You write the profile minimally (see "Copy these shapes"): a current server fills `family_key`, `method_version`, `family_description`, each property's `description` and `reason`, the profile's `normalized_context` (taken from the record's classification, replacing a wrong one), the record's `technical.client_analysis_metadata`, and the `technical.profile_key` when the catalog holds one profile. Each replacement is listed in `derived.values`.
- On a configurable record (several variants) a compliance or certification claim that has no download cannot be `product-specific`: bind it to a combination-scoped download occurrence, use the scope the evidence supports, or record it as a technical property.
- The file-based tools: validate accepts a request file without `job_id`; the job needs the validation's `job_binding`, so validate once without it, create the job, then add `job_id` and the chunk `idempotency_key` to the file and validate again (same request digest) before preparing the stage intent from the file. On a hosted MCP these tools do not exist; use the chunk handle below.
- A platform administrator's validation also needs the routing manifest: `submission.record_manifest`, an array (not an object) of `{ "external_record_id": "<id>", "routing": { "destination": { "mode": "vendor", "vendor_id": "<uuid>" } } }`, one per record. Omit its digest; the server derives it. A wrong shape can surface as `product_discovery_scope_required` or `routing_manifest_required`; read `issues[]` for the real cause.
- The file-based validate tool (present only on a local MCP) reads files only from the folder configured on the MCP host, not from your working directory. A remote or plugin-only client should send `specsket_validate_records` with the payload inline.
- An empty `product_variant_applicability` `occurrences` list is accepted, and every download, technical group and installation item then shows as "All variants" in the review screen. A product sheet for one size or SKU (for example "A06GICMR-WHE.N0X0P (60x60cm)") needs a `download` occurrence scoped to that combination; leave "All variants" only for files that really cover the whole family (a shared test-method datasheet). Check the review screen's Download tab against the source before calling the job complete.
- Validation checks request-level shape first. A stripped-down probe returns only top-level errors, so send the real payload and read every `issues[]` entry before fixing one.

- The outer `evidence_refs` of `technical.properties` must equal exactly the union of all nested observation `evidence_refs` (`technical_property_outer_evidence_mismatch` on older servers; a current server derives the outer list and reports a change in `derived.values`).
- Receipts (validation, execution, scope) are long signed strings. Never retype or retype-from-memory a receipt: one wrong character gives a generic `product_execution_receipt_stale`. Save each response to a file and read the value from it programmatically.
