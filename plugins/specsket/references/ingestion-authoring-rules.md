# Product ingestion: extraction and authoring rules

Moved verbatim from the ingestion skill so the procedure stays short. Read all of it before the first field preview of a session; every rule is as binding as the skill itself. A rule kept in another reference is named here by section instead of repeated.

## Sources, documents and certifications

Extract from the rendered page, not a static fetch alone ([rendered-page extraction](rendered-page-extraction.md)), and model Technical Data by the ingestion preview contract's "Technical Data modelling".

For a supplied product, family, collection, category, or catalogue URL, follow the workflow contract's visible source review before and during extraction: open the supplied page in the in-app browser by default, show each exact official product page as it is checked, and leave the most relevant product page open for the user. Do not use mobile mode or device emulation unless the user requests mobile verification or desktop presentation is unavailable. Structured extraction may run alongside the visible pass; browser visibility does not replace exact field evidence.

Analyze attached client files before making product-specific MCP calls. Follow [the client analysis contract](./client-analysis-contract.md), create resumable family checkpoints for large batches, and keep every value evidence-bound. A local path alone does not make files available to the assistant; inspect only files the host actually exposes.

When the user supplies an official product, family, collection, category, or catalogue URL, declare the selection scope before extraction (cap unit, counts and continuation: workflow contract step 5). Use `parent_product` by default for collection/category requests; use `orderable_source_identity` only for an explicit exact-item request and `category_occurrence` only for a per-category request. Represent a finite selection as `cap_mode: bounded` with a positive product-selection cap, or use `cap_mode: all_discovered` without a product cap. Keep crawl/page/byte/evidence/cost budgets separate: exhausting an operational budget makes discovery unresolved and requires continuation or scope revision. Representative sampling is allowed only when explicitly requested as `exact_identity_subset` and must remain labeled partial. Inventory the supplied page first, then follow relevant manufacturer-controlled links and official documents.

Read every official document linked from the product page, and the vendor's site-wide download or accreditation pages it links to, for facts on every product, not only when identifiers are missing (the ingestion preview contract's "Field coverage and source documents"). When the product page lacks an orderable matrix, inspect prominent official datasheets, schedules, order guides, specifications, and catalogues before concluding that identifiers are unavailable. Extract tables row by row, carry merged or grouped headers into each row, and bind the official identifier to the exact documented edge, size, thickness, color/finish, performance, and packaging tuple. Manufacturer-labeled Item Numbers and equivalent order identifiers may serve as variant SKUs while retaining their original identity kind and PDF page/table evidence. Do not invent rows or multiply independent option pools.

Download all documents and images for a product in one shell step, not one command per file: run the downloads together, at most three at a time, try each file at most twice, and stop retrying after the second failure. If a file still fails after two tries, record it as unavailable with its address and the error, carry on without it, and say so in the report; do not keep retrying or switch to a different maker. A document you could not download is not a reason to leave the field blank: use the page text for the field when the page states it, and note the missing file in the quality gate.

Certifications follow the ingestion preview contract's "Certification discovery and accounting": expand manufacturer-controlled certification accordions, download modals, tabs, selector panels, and other interactive certification surfaces; record every literal label, compare selector states, and count occurrences by its rule (never leave `certification_coverage` at 0 when the source lists such documents). That accounting is a completion gate: show literal detected, normalized, excluded, and unresolved counts and names, with each encountered label assigned to exactly one outcome. On a configurable record, every normalized product-specific certification must set `applicability_occurrence_id` to its normalized combination-scoped Download applicability occurrence; that occurrence must retain the exact combination IDs and SKU aliases.

Inspect every provided file available in the current conversation. Preserve the source filename, MIME type, original-byte SHA-256 when the host exposes the bytes, and exact per-field locator.

## Live schema, preview and topology choice

Make sure the authoring kit (or `specsket_get_capabilities`) has been read before claiming a complete field preview; without either, follow the [no live Specsket connection](./ingestion-conditional-no-live-specsket-connection.md).

Require `product_ingestion.validate` before normalizing and `product_ingestion.stage` before offering to stage (the kit's `workflow` holds both). The kit carries the `current` product schema and the compact presentation contracts; without the kit, follow the [no authoring kit](./ingestion-conditional-no-authoring-kit.md). Never hard-code a schema version, wrapper shape, or field IDs from UI labels or old examples.

The research contract's `field_catalog` is the live human-readable Product Wizard hierarchy. Use it to explain and organize fields, but never submit it as the entity schema or presentation envelope. If the user asks for all available fields during ingestion, answer by the field catalog contract.

After bounded discovery and schema retrieval, render the complete pre-validation preview required by the ingestion preview contract, organized by the live field catalog; include every returned current-schema field (as a row, or by field ID in the summary line of the layout chosen under the ingestion preview contract's "Preview layout"). Complete this preview before offering the immutable topology choice or a final validation summary.

Only after the preview completion gate passes, show the recommended product structure, resulting product-record count, documented combination counts, unsupported orderable axes, and unresolved source nodes. Let the user keep the recommendation or explicitly choose separate product records. Treat that pre-staging choice as immutable for the job; changing it requires rebuilding the presentation envelope, revalidation, a refreshed preview for affected fields, and a new confirmation summary.

In every shortlist, selected-product list, topology recommendation, and final pre-validation summary, start with `Recommended scope: N products` and display each product name as a clickable exact official product-detail URL. Include manufacturer, recommendation reason, proposed structure/count, coverage status, and unresolved source nodes. Do not substitute a collection/search URL for an available product-detail URL or leave the exact link only inside a checkpoint or field table.

## Discovery scope and readiness

When capabilities enable `product_discovery_scope_contract`, this is the current procedure and the legacy coverage `@1` rules ([older Specsket](./ingestion-conditional-older-specsket-without-product-discovery-scope-contract.md)) do not apply. Follow the skill's strict sequence for upload, finalize and execution; the server derives the digests. Partitions may span several validation chunks or jobs (not available plugin-only: use one chunk per partition). Every partition and chunk-local `product-source-coverage@2` sidecar binds the same scope digest and execution partition digest. Inventory every discovered source parent and category occurrence; every documented orderable identity; selected, excluded, and unresolved dispositions; output-parent split lineage; official evidence; and global counts. Preserve the manufacturer's literal identity type. An exact manufacturer-SKU request filters strictly to `manufacturer_sku`; other exact-item requests may use any official orderable identity. Never relabel another identifier or canonical URL as a manufacturer SKU; a generated `SRC-...` value is internal only. Pass only records in the current validation/staging chunk through coverage `@2`; do not duplicate the complete batch manifest in every chunk. Omitted or duplicated identities across output records, chunks, or jobs block execution completion. Scope-less or coverage `@1` history is `Legacy scope unverified` (ingestion preview contract, "Completion gate").

When capabilities require `product-readiness@1`, build it automatically, by the product readiness contract, for every standalone product and output parent after discovery scope and before validation. Missing or changed readiness cannot be acknowledged away or downgraded through an older wrapper.

## Profiles and technical properties

When capabilities advertise `analysis_location: client`, do not call specification-analysis start, poll, or assessment tools. The assistant owns file inspection, cross-file product linking, family grouping, dynamic profile creation, and evidence mapping. Infer which properties are relevant to the family, but never infer an unsupported property value. Preserve `not_found`, `insufficient_evidence`, `conflicting_evidence`, `not_applicable`, and `requires_vendor_confirmation` explicitly.

Group only genuinely equivalent product contexts. Submit each family profile once in the request-level `product_profile_catalog`; each record references its `technical.profile_key` and carries record-specific observations, trace, metadata, and evidence. Use only the live schema's generated submission contract and limits.

When the current schema is `product@3`, include every profile property's explicit record state, value origin, value, unit, test/classification system, scope, and nested evidence references. The outer field evidence is the exact union of all nested references, including every conflicting reference; the server fills it when you leave it out and corrects a wrong one (reported in `repaired`). Do not submit snapshot IDs or profile/assessment digests; validation calculates and signs those outputs. Only `unit_conversion@1` may be submitted as derived, and only when the generated live contract can be satisfied exactly.

## Presentation, variants, applicability and images

When capabilities advertise `product-presentation@1`, keep the `product@2` or `product@3` entity submission unchanged and add presentation data only through the advertised route wrapper. Use only Colors, Dimensions, and Material Finish as selectable axes. Put unsupported shared facts in all-variant Technical Data; put non-selectable varying facts in combination-scoped Technical Data; split records when an unsupported field is required to order distinct manufacturer identifiers. Submit exact documented combinations, a stable `external_key` on every object (ids are derived from it; supply ids only on an older Specsket without `chunk_id_derivation`), structured dimension thickness, typed source identities, explicit SKU origin, group scope by combination ID, and applicability evidence. Use the same presentation envelope for validation and staging. A changed topology, option tuple, scope, warning, or record count requires revalidation and a refreshed confirmation summary.

Before validation, calculate the supported-axis tuple for every typed source identity and prove the tuples are one-to-one within each proposed parent record. Never create a selectable SKU, article, product-code, item-code, `documented-sku`, canonical-URL, or synthetic exact-state axis and never disguise one with the Colors, Dimensions, or Material Finish preset. If two distinct identities collapse to the same supported-axis tuple, or an identity lacks a required supported-axis value, split the affected topology without losing identities, ask for confirmation, or explicitly exclude the parent. Read `max_combinations_per_output_parent` and its digest from live capabilities; fail closed when the limit is missing or inconsistent. A numeric ceiling is not permission to truncate, sample, or relabel source identity as a supported axis.

Treat the capability-advertised presentation version as authoritative. Under `product-presentation@2` or later, bind one explicit primary image-bearing selector axis and assign every enabled documented combination exactly one image-resolution state: `exact_combination_override`, `inherited_selector_value`, `parent_fallback`, or `unresolved`. An exact override requires identity- or tuple-specific official evidence and outranks selector inheritance. Selector inheritance requires an evidenced image on the selected primary option value. Parent fallback is allowed only when the source supports that role and the payload opts in explicitly. An unresolved combination must stay image-less, suppress parent fallback, and appear in the topology unresolved nodes. Never derive exact combination ownership from a filename, URL slug, visual similarity, selector representative identity, or nearby card.

When `product-presentation@3` is advertised, use its evidence-bound `media_references` and `parts` instead of inferring ownership during staging. Preserve stable media/part IDs, exact owner kind and ID, role, supplied URL byte string, order, and evidence. Map option, combination, product, project, part, wireframe, and technical-drawing roles exactly as the live contract advertises. A part image must depict or explicitly bind the physical part; missing exact part evidence leaves it image-less. Keep modern master parts and per-combination BOM entries logically singular rather than duplicating the same part into legacy material parts. (On a current server combination and selector-value images are the exception: see the ingestion validation gotchas.)

When capabilities advertise `product-variant-applicability@1`, build that sidecar automatically for every product URL or file ingestion; the user does not need to call it separately. Apply it generically to every relevant Technical Data group/card, installation item, Download entry in every section, and compatible-product relationship. Discover all relevant features rather than an allowlist such as slip/use/3D Ink: include material, performance, technology, premium features, certifications, instructions, documents/references, and relationships wherever official evidence exposes them. Classify each source occurrence as `normalized`, `excluded`, or `unresolved`; use `all_variants` only with evidence that it is shared, use exact documented combination IDs and SKU aliases for scoped facts, and never guess scope. Technical groups bind their existing presentation-group scope instead of duplicating it. Preserve stable occurrence IDs and exact content/applicability evidence so repeated labels remain separately accountable and compatible relationships can aggregate multiple evidence occurrences without duplicating the relationship.

Download extraction is not upload-only: normalize files and source references as the ingestion preview contract's "Documents and applicability" describes.

Build a source-image inventory before mapping media, and route it by the ingestion preview contract's "Images" (including "Parent primary image" and its physical-versus-logical accounting). Put only canonical parent/product images in `media.images`; put the product's other photos (extra views, close-ups) and project/application scenes in `media.project_images`, selector-value images on their presentation option values, and exact combination images on their presentation combinations. Attach an exact evidence locator to every image association. Select exactly one product-owned primary for each output parent and place its URL first in `media.images`, followed by the same canonical gallery order; a representative member image requires explicit evidence and the represented identity. Reconcile the combination coverage totals before validation.

## Host tool checks and validation

Before validating, on every host (checking the callable tool declarations costs nothing): Fail closed before job creation unless the callable tool declarations preserve `product_presentation`, `product_variant_applicability`, capability-required `product_readiness`, `chunk_index`, `topology_manifest`, `destination_plan`, `external_record_ids`, validation receipts, content/request digests, and the required presentation/applicability/readiness binding inputs for the advertised contract. A schema document that describes those fields does not compensate for a host adapter that strips them. The only allowed omission is `destination_plan.destination_contract_version` under `destination_contract_binding: server_default_when_omitted` (workflow contract step 8); the destination plan itself and every routing field must still be callable, and any other missing field remains a hard stop.

Validate the complete submission. Resolve every error through the same schema/taxonomy/validation path. Warnings may be presented to the user but must not be silently discarded. Refresh receipts as workflow contract step 10 says; unchanged revalidation does not need a second confirmation, but any changed warnings, mappings, assessment, destination, or count does. An expired untouched original follows the renewal rule in [an untouched original whose permission expired](./ingestion-conditional-an-untouched-original-whose-permission-expired.md).
