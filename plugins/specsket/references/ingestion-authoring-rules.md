# Product ingestion: extraction and authoring rules

Moved verbatim from the ingestion skill so the procedure stays short. Read all of it before the first field preview of a session; every rule is as binding as the skill itself.

## Sources, documents and certifications

Extract from the rendered page, not a static fetch alone (see the workflow contract's "Rendered-page extraction"), and model Technical Data with the groups, cards and attributes rule in the ingestion preview contract: key/value rows become parameter groups, narrative text becomes cards, and each selector that publishes its own identifier or image becomes a documented variant.

For a supplied product, family, collection, category, or catalogue URL, follow the workflow contract's visible source review before and during extraction: open the supplied page in the in-app browser by default, select desktop site or desktop viewport mode and the largest practical panel when those controls exist, show each exact official product page as it is checked, and leave the most relevant product page open for the user. Do not use mobile mode or device emulation unless the user requests mobile verification or desktop presentation is unavailable. Structured extraction may run alongside the visible pass; browser visibility does not replace exact field evidence.

Analyze attached client files before making product-specific MCP calls. Follow [the client analysis contract](./client-analysis-contract.md), create resumable family checkpoints for large batches, and keep every value evidence-bound. A local path alone does not make files available to ChatGPT; inspect only files the host actually exposes.

When the user supplies an official product, family, collection, category, or catalogue URL, declare the selection scope before extraction. Use `parent_product` by default for collection/category requests; use `orderable_source_identity` only for an explicit exact-item request and `category_occurrence` only for a per-category request. Represent a finite selection as `cap_mode: bounded` with a positive product-selection cap, or use `cap_mode: all_discovered` without a product cap. Keep crawl/page/byte/evidence/cost budgets separate: exhausting an operational budget makes discovery unresolved and requires continuation or scope revision. Every selected parent retains all documented in-scope orderable identities. Representative sampling is allowed only when explicitly requested as `exact_identity_subset` and must remain labeled partial. Inventory the supplied page first, then follow relevant manufacturer-controlled links and official documents. Never create variants by multiplying independent option lists.

Read every official document linked from the product page, and the vendor's site-wide download or accreditation pages it links to, for facts on every product, not only when identifiers are missing; follow the ingestion preview contract's "Field coverage and source documents" and account for every active catalog field. When the product page lacks an orderable matrix, inspect prominent official datasheets, schedules, order guides, specifications, and catalogues before concluding that identifiers are unavailable. Extract tables row by row, carry merged or grouped headers into each row, and bind the official identifier to the exact documented edge, size, thickness, color/finish, performance, and packaging tuple. Manufacturer-labeled Item Numbers and equivalent order identifiers may serve as variant SKUs while retaining their original identity kind and PDF page/table evidence. Do not invent rows or multiply independent option pools.

Expand manufacturer-controlled certification accordions, download modals, tabs, selector panels, and other interactive certification surfaces that are visible on the official page. Record every literal certification label, including repeated labels, before normalizing references. For configurable products, compare certification results across every distinct selector state represented by documented combinations. Reuse one coverage state only after the official UI proves those selector states expose the same certification set; do not multiply a collection-level certificate across SKUs or imply SKU applicability merely because it appears on the collection page.

Count certifications by the rule in the ingestion preview contract: third-party certificates, EPD/HPD declarations, Declarations of Performance (CE) and independent test reports are certification occurrences and also Download entries; a manufacturer's self-declaration counts but is labelled as a manufacturer claim; brochures and datasheets never count. Do not leave `certification_coverage` at 0 when the source lists such documents.

The preview's certification accounting is a completion gate. Show literal detected, normalized, excluded, and unresolved counts and names, with each encountered label assigned to exactly one outcome. Preserve duplicate labels as separate detected occurrences until their evidence and modal behavior prove they are the same reference. A certification with no file URL remains visible as a source-page reference with its actual availability state and bounded next action; never fabricate a download URL. Manufacturer or corporate certifications must retain manufacturer-level applicability instead of being promoted to product, family, selector, combination, or SKU evidence. On a configurable record, every normalized product-specific certification must set `applicability_occurrence_id` to its normalized combination-scoped Download applicability occurrence; that occurrence must retain the exact combination IDs and SKU aliases.

Inspect every provided file available in the current conversation. Preserve the source filename, MIME type, original-byte SHA-256 when the host exposes the bytes, and exact per-field locator. Use taxonomy search for functional categories and CSI rather than freehand IDs.

## Live schema, preview and topology choice

After the initial source inventory and before claiming a complete field preview, make sure the authoring kit (or `specsket_get_capabilities`) has been read. If neither tool is available, or the **Specsket MCP Tools Beta** connection is unavailable, stop the live staging phase and explain that the public plugin supplies instructions but live Specsket access requires a separate Streamable HTTP MCP connection to `https://integrations.specsket.com/mcp`, followed by Specsket OAuth and a new chat. Do not infer the user's identity, permissions, destination, schemas, or live Specsket state, and do not claim that the current-schema preview was completed, anything was validated, or anything was staged.

Require `product_ingestion.validate` before normalizing and `product_ingestion.stage` before offering to stage (the kit's `workflow` holds both). The kit carries the `current` product schema and the compact presentation contracts; without the kit, fetch the `current` product schema through `specsket_get_entity_schema`; when product presentation is advertised, set `include_product_presentation_contracts` to true. The presentation contracts arrive compact by default: `{ "$ref": "#/shared_schemas/<name>" }` stands for the schema stored under `product_presentation_contracts.shared_schemas.<name>`; follow it when you need that shape, and set `presentation_contract_view` to `full` only if you cannot. Never hard-code a schema version, wrapper shape, or field IDs from UI labels or old examples.

The research contract's `field_catalog` is the live human-readable Product Wizard hierarchy. Use it to explain and organize fields, but never submit it as the entity schema or presentation envelope. If the user asks for all available fields during ingestion, show the complete active catalog grouped by tab and section and keep compatibility, presentation, and contextual dynamic descriptors separate.

After bounded discovery and schema retrieval, render the complete pre-validation preview required by the ingestion preview contract. Use the live field catalog for friendly tab and section organization, include every returned current-schema field, and show literal detected values or counts, proposed mappings, evidence/status, scope, and next action. Make image and document URLs clickable and preserve document availability separately from applicability. Complete this preview before offering the immutable topology choice or a final validation summary.

Only after the preview completion gate passes, show the recommended product structure, resulting product-record count, documented combination counts, unsupported orderable axes, and unresolved source nodes. Let the user keep the recommendation or explicitly choose separate product records. Treat that pre-staging choice as immutable for the job; changing it requires rebuilding the presentation envelope, revalidation, a refreshed preview for affected fields, and a new confirmation summary.

In every shortlist, selected-product list, topology recommendation, and final pre-validation summary, start with `Recommended scope: N products` and display each product name as a clickable exact official product-detail URL. Include manufacturer, recommendation reason, proposed structure/count, coverage status, and unresolved source nodes. Do not substitute a collection/search URL for an available product-detail URL or leave the exact link only inside a checkpoint or field table.

## Discovery scope and readiness

When capabilities enable `product_discovery_scope_contract`, this is the current procedure and the legacy coverage `@1` rules in the conditional rules reference do not apply. Follow the strict sequence above for upload, finalize and execution; the server derives the digests. Partitions may span several validation chunks or jobs (not available plugin-only: use one chunk per partition). Every partition and chunk-local `product-source-coverage@2` sidecar binds the same scope digest and execution partition digest. Inventory every discovered source parent and category occurrence; every documented orderable identity; selected, excluded, and unresolved dispositions; output-parent split lineage; official evidence; and global counts. Preserve the manufacturer's literal identity type. An exact manufacturer-SKU request filters strictly to `manufacturer_sku`; other exact-item requests may use any official orderable identity. Never relabel another identifier or canonical URL as a manufacturer SKU. A generated `SRC-...` value is internal only. Pass only records in the current validation/staging chunk through coverage `@2`; do not duplicate the complete batch manifest in every chunk. Omitted or duplicated identities across output records, chunks, or jobs block execution completion. Scope-less or coverage `@1` history is `Legacy scope unverified` and cannot claim parent completeness.

When capabilities require `product-readiness@1`, build it automatically for every standalone product and output parent after discovery scope and before validation. Bind each record to its immutable source/output parent, exact source-backed grouping and display name, and exactly one evidenced product-owned primary media reference. Pass the identical sidecar through validation and staging; the per-record digest map comes from the validation `job_binding`. Missing or changed readiness cannot be acknowledged away or downgraded through an older wrapper.

## Profiles and technical properties

When capabilities advertise `analysis_location: client`, do not call specification-analysis start, poll, or assessment tools. ChatGPT owns file inspection, cross-file product linking, family grouping, dynamic profile creation, and evidence mapping. Infer which properties are relevant to the family, but never infer an unsupported property value. Preserve `not_found`, `insufficient_evidence`, `conflicting_evidence`, `not_applicable`, and `requires_vendor_confirmation` explicitly.

Group only genuinely equivalent product contexts. Submit each family profile once in the request-level `product_profile_catalog`; each record references its `technical.profile_key` and carries record-specific observations, trace, metadata, and evidence. Use only the live schema's generated submission contract and limits.

When the current schema is `product@3`, include every profile property's explicit record state, value origin, value, unit, test/classification system, scope, and nested evidence references. The outer field evidence must be the exact union of all nested references, including every conflicting reference. Do not submit snapshot IDs or profile/assessment digests; validation calculates and signs those outputs. Only `unit_conversion@1` may be submitted as derived, and only when the generated live contract can be satisfied exactly.

## Presentation, variants, applicability and images

When capabilities advertise `product-presentation@1`, keep the `product@2` or `product@3` entity submission unchanged and add presentation data only through the advertised route wrapper. Use only Colors, Dimensions, and Material Finish as selectable axes. Put unsupported shared facts in all-variant Technical Data; put non-selectable varying facts in combination-scoped Technical Data; split records when an unsupported field is required to order distinct manufacturer identifiers. Submit exact documented combinations, a stable `external_key` on every object (ids are derived from it; supply ids only on an older Specsket without `chunk_id_derivation`), structured dimension thickness, typed source identities, explicit SKU origin, group scope by combination ID, and applicability evidence. Use the same presentation envelope for validation and staging. Take its topology manifest, `product_structure_digest` and per-record presentation digests from the validation `job_binding` when creating the job. A changed topology, option tuple, scope, warning, or record count requires revalidation and a refreshed confirmation summary.

Before validation, calculate the supported-axis tuple for every typed source identity and prove the tuples are one-to-one within each proposed parent record. Never create a selectable SKU, article, product-code, item-code, `documented-sku`, canonical-URL, or synthetic exact-state axis and never disguise one with the Colors, Dimensions, or Material Finish preset. If two distinct identities collapse to the same supported-axis tuple, or an identity lacks a required supported-axis value, split the affected topology without losing identities, ask for confirmation, or explicitly exclude the parent. Read `max_combinations_per_output_parent` and its digest from live capabilities; fail closed when the limit is missing or inconsistent. A numeric ceiling is not permission to truncate, sample, or relabel source identity as a supported axis.

Treat the capability-advertised presentation version as authoritative. Under `product-presentation@2` or later, bind one explicit primary image-bearing selector axis and assign every enabled documented combination exactly one image-resolution state: `exact_combination_override`, `inherited_selector_value`, `parent_fallback`, or `unresolved`. An exact override requires identity- or tuple-specific official evidence and outranks selector inheritance. Selector inheritance requires an evidenced image on the selected primary option value. Parent fallback is allowed only when the source supports that role and the payload opts in explicitly. An unresolved combination must stay image-less, suppress parent fallback, and appear in the topology unresolved nodes. Never derive exact combination ownership from a filename, URL slug, visual similarity, selector representative identity, or nearby card.

When `product-presentation@3` is advertised, use its evidence-bound `media_references` and `parts` instead of inferring ownership during staging. Preserve stable media/part IDs, exact owner kind and ID, role, supplied URL byte string, order, and evidence. Map option, combination, product, project, part, wireframe, and technical-drawing roles exactly as the live contract advertises. A part image must depict or explicitly bind the physical part; missing exact part evidence leaves it image-less. Keep modern master parts and per-combination BOM entries logically singular rather than duplicating the same part into legacy material parts. (Added 6 Nov 2026: on a current server, combination and selector-value images are the exception. Give `image_urls` or `image_url` with evidence and leave out their media references and reference ids; the server creates them, as the ingestion validation gotchas describe.)

When capabilities advertise `product-variant-applicability@1`, build that sidecar automatically for every product URL or file ingestion; the user does not need to call it separately. Apply it generically to every relevant Technical Data group/card, installation item, Download entry in every section, and compatible-product relationship. Discover all relevant features rather than an allowlist such as slip/use/3D Ink: include material, performance, technology, premium features, certifications, instructions, documents/references, and relationships wherever official evidence exposes them. Classify each source occurrence as `normalized`, `excluded`, or `unresolved`; use `all_variants` only with evidence that it is shared, use exact documented combination IDs and SKU aliases for scoped facts, and never guess scope. Technical groups bind their existing presentation-group scope instead of duplicating it. Preserve stable occurrence IDs and exact content/applicability evidence so repeated labels remain separately accountable and compatible relationships can aggregate multiple evidence occurrences without duplicating the relationship.

Download extraction is not upload-only. Normalize both obtained files and source references that have a title, description, availability, official source-page URL, and applicability even when no direct file URL exists. Keep certificates in Download as file/reference entries; keep non-document technical features in Technical Data & Specification. Installation and compatible-product entries use the same all/specific/unresolved applicability semantics. A user may later create or edit these file/reference entries manually without fabricating a file.

Build a source-image inventory before mapping media. The product page's own main displayed image (default carousel or gallery slide, even a room render of this exact product) is the parent primary; never leave the parent without a primary while swatches or variant images exist and the page shows a product image (see the ingestion preview contract's "Parent primary image"). Put only canonical parent/product images in `media.images`; keep project/application scenes in `media.project_images`, selector-value images on their presentation option values, and exact combination images on their presentation combinations. Attach an exact evidence locator to every image association. Select exactly one product-owned primary for each output parent and place its URL first in `media.images`, followed by the same canonical gallery order. A representative member image requires explicit evidence and the represented identity. Report physical source counts separately from logical parent, selector, combination, project, duplicate, excluded, and unresolved associations, and reconcile the combination coverage totals before validation.

## Host tool checks and validation

Fail closed before job creation unless the callable tool declarations preserve `product_presentation`, `product_variant_applicability`, capability-required `product_readiness`, `chunk_index`, `topology_manifest`, `destination_plan`, `external_record_ids`, validation receipts, content/request digests, and the required presentation/applicability/readiness binding inputs for the advertised contract. A schema document that describes those fields does not compensate for a host adapter that strips them. One compatibility exception is allowed for `destination_plan.destination_contract_version`: when the live capabilities return `destination_contract_binding: server_default_when_omitted`, the callable declaration may omit only that nested version field because the MCP deterministically inserts the simultaneously advertised `destination_contract_version` before request-digest verification and persistence. The destination plan itself and every routing field must still be callable; any other missing field remains a hard stop.

Validate the complete submission. Resolve every error through the same schema/taxonomy/validation path. Warnings may be presented to the user but must not be silently discarded. Before preparing a new durable original or staging an ordinary unprepared chunk, refresh its validation receipt when less than 120 seconds remain; unchanged revalidation does not need a second confirmation, but any changed warnings, mappings, assessment, destination, or count does. Once an original is prepared, never replace its immutable saved receipt or payload with a refreshed one. An expired untouched original follows the renewal rule in [conditional rules](./ingestion-conditional-rules.md).
