# Ingestion gotchas: staging and large answers

Read "Large responses" at the start of a run and the rest before staging a validated chunk. Rules for the scope are in [ingestion scope gotchas](ingestion-gotchas-scope.md); rules for the chunk in [ingestion validation gotchas](ingestion-validation-gotchas.md).

## Large responses

- `specsket_get_entity_schema` with presentation contracts is about 80 KB and `specsket_read_vendor_storefront` with `context`, `draft`, `readiness` and `contract` together is about 110 KB. Many clients refuse results over their token limit and save them to a file. Ask for `contract` or the presentation contracts once, on their own, and read only the keys you need from the saved file. Do not use `jq`; it may not be installed.

## Staging path

- Write the scope, execution, job and operation ids to a state file after every write (at the latest as soon as a stage intent is prepared) so an interrupted run can resume without creating a duplicate.
- On a local Specsket, `specsket_dispatch_product_chunk_stage_intent` fails with `chunk_local_storage_unavailable` (issue `local_storage_selection_disabled`) until the runtime owner has enrolled and selected a local product storage caller for that exact job after the human authorized it. An agent cannot do this through the MCP and must not work around it. The prepared intent stays valid; report the job id and operation id, ask for the enrolment, then dispatch the same operation. Capabilities `runtime_mode_readiness: ready` does not mean a caller is selected.
- Do not resend a large chunk. On a Specsket MCP 0.41.0 or later, a product validation answer (success or failure) carries `chunk_cache.handle`, good for 15 minutes on that server: fix a failed chunk with `specsket_validate_records` `base_chunk` (the handle) plus `patch`, a JSON Patch list of `add`, `replace` and `remove` operations whose paths start at `/submission`, `/product_presentation`, `/product_variant_applicability`, `/source_coverage`, `/product_readiness` or `/chunk_index` (for example `{"op":"replace","path":"/submission/records/0/fields/information.description/value","value":"..."}`), and stage a chunk that passed with `specsket_prepare_product_chunk_stage_intent` `chunk_handle` instead of its contents. A "no longer cached" answer (expired, server restart, or a different sign-in; from MCP 0.45.0 a refreshed admin login keeps the cache) means validate the full payload once more, which returns the same handle, then repeat the call; the cache is only a convenience.
- On a Specsket MCP that accepts it (0.40.0 and later), do not hand-build `stage_request`: call `specsket_prepare_product_chunk_stage_intent` with the same `submission`, sidecars and `chunk_index` you validated, plus `validation_receipt`, the chunk `idempotency_key`, a stable `operation_id` and `expected_job_updated_at` from `specsket_get_ingestion_job`. Passing both that and `stage_request` is refused. Only on an older MCP: `stage_request` is the stage request, not the validation request. With applicability and `product-source-coverage@2` it is exactly: `{ "request_contract": "<capabilities product_variant_applicability_contract.stage_request_contract>", "entity_submission": <the validated submission, with record_manifest>, "product_presentation": <envelope>, "product_variant_applicability": <envelope>, "source_coverage": <manifest>, "product_readiness": <only when readiness is on>, "staging": { "job_id", "chunk_index", "idempotency_key", "validation_receipt" } }` with no other root keys. The sidecars sit beside `entity_submission`, never inside it, and `staging.content_digest` is optional. Use the same chunk `idempotency_key` you will not change, plus a separate stable `operation_id` and an `expected_job_updated_at` read from `specsket_get_ingestion_job`.
