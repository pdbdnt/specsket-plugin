# Ingestion gotchas: staging and large answers

Read "Large responses" at the start of a run and the rest before staging a validated chunk. Rules for the scope are in [ingestion scope gotchas](ingestion-gotchas-scope.md); rules for the chunk in [ingestion validation gotchas](ingestion-validation-gotchas.md).

## Large responses

- `specsket_get_entity_schema` with presentation contracts is about 80 KB and `specsket_read_vendor_storefront` with `context`, `draft`, `readiness` and `contract` together is about 110 KB. Many clients refuse results over their token limit and save them to a file. Ask for `contract` or the presentation contracts once, on their own, and read only the keys you need from the saved file. Do not use `jq`; it may not be installed.

## Staging path

- Write the scope, execution, job and operation ids to a state file after every write (at the latest as soon as a stage intent is prepared) so an interrupted run can resume without creating a duplicate.
- Do not resend a large chunk. On a Specsket MCP 0.41.0 or later, a product validation answer (success or failure) carries `chunk_cache.handle`, good for 15 minutes on that server: fix a failed chunk with `specsket_validate_records` `base_chunk` (the handle) plus `patch`, a JSON Patch list of `add`, `replace` and `remove` operations whose paths start at `/submission`, `/product_presentation`, `/product_variant_applicability`, `/source_coverage`, `/product_readiness` or `/chunk_index` (for example `{"op":"replace","path":"/submission/records/0/fields/information.description/value","value":"..."}`), and stage a chunk that passed with `specsket_stage_validated_chunk` `chunk_handle` instead of its contents. A "no longer cached" answer (expired, server restart, or a different sign-in; from MCP 0.45.0 a refreshed admin login keeps the cache) means validate the full payload once more, which returns the same handle, then repeat the call; the cache is only a convenience.
- Staging a chunk whose partition already has a job (a new job key, the same chunk index) is refused with 409 `integration_conflict`, "The ingestion chunk idempotency identity is already bound to different content." For a claimed partition that wording means the partition is already claimed by an existing job: read that job (`specsket_get_ingestion_job`) and its stage intent, reconcile or finish it, and do not create another job for the same partition. A new job needs a new partition (a new scope or execution).
- On a Specsket MCP that accepts it (0.40.0 and later), do not hand-build `stage_request`: call `specsket_prepare_product_chunk_stage_intent` with the same `submission`, sidecars and `chunk_index` you validated, plus `validation_receipt`, the chunk `idempotency_key`, a stable `operation_id` and `expected_job_updated_at` from `specsket_get_ingestion_job`.
