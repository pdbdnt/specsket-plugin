# Ingestion gotchas: the discovery scope

Read before uploading a discovery-scope fragment. Rules for the chunk are in [ingestion validation gotchas](ingestion-validation-gotchas.md); rules for staging in [ingestion staging gotchas](ingestion-gotchas-staging.md).

## Scope fragment (before upload)

- Every source parent needs `category_occurrences` (send `[]` when you scope by parent product). `checkpoint_ref` is not a key of `execution_partitions`; it belongs to the chunk's `product_presentation.product_structure.checkpoint_ref` (the job's topology checkpoint). A scope upload rejects unknown keys with `Unrecognized key(s)` and a missing one with a bare `Required`; read `issues[].path`.
- Omit `authority_key` on a source parent: the server derives it, and a different value fails as `source_parents.N.authority_key` differing from the derived one. Send it only by copying the exact expected value from that message.
- Before uploading the scope, list every evidence id the chunk will cite anywhere (field values, presentation properties, ordering or product-number tables, media, coverage) as an evidence binding of the partition it belongs to. An id the chunk cites that the scope did not bind to that partition fails validate with 409 `product_discovery_evidence_binding_mismatch` ("evidence X is not bound to execution partition Y").
- Key names differ by object. Source parents and orderable variants carry `key`; each output parent carries `output_parent_id` (a `key` there is rejected with `Unrecognized key(s)`); each execution partition needs `partition_id` and `orderable_variant_ids` (both fail with a bare `Required` when missing). `scope_id` is a UUID you generate once (36 characters with dashes), not a name.
- Every orderable variant's `canonical_identity` must also appear in its `identity_aliases`. The server adds `orderable_variant_id` when you omit it.
- `product_discovery_evidence_binding_mismatch` names the evidence id and partition; for an id the scope does not bind, `issues[].expected` lists the evidence ids it does bind. "has no evidence_catalog entry" means the scope predates `chunk_scope_evidence_reuse` (or bound digests only), so include the exact uploaded entry; "not byte-identical" means a repeated entry differs from the uploaded one: omit it (with `chunk_scope_evidence_reuse`) or resend it exactly. `issues[].path` names the entry and `expected` its uploaded digest. Evidence the scope does not bind to the partition is new evidence: give it a new `evidence_id`.
- Upload with the scope every source the chunk will cite, including each PDF, datasheet or drawing, as the `source` of an evidence binding in that partition: the job takes its sources only from the scope partition, so a chunk cannot add one (`chunk_source_not_in_scope`). Bind there too every evidence item the chunk's coverage will cite, including the `evidence_refs` of each download written once with `write_once_applies_to`, because the server turns that download into a coverage entry.
- `product_discovery_variant_identity_mismatch`: an inspected selector state's `source_identity` is not one of the identities the scope recorded for that record's variants (`issues[].expected` lists the scope's canonical identities still unmatched). Use the uploaded `canonical_identity` or an `identity_aliases` entry; two states naming one variant fail with `product_discovery_variant_identity_duplicate`.
- Downloads and coverage name the same files (matched by file URL, ignoring http/https and a leading `www.`). Every `downloads.technical_files` or `downloads.documents` item with a URL needs a `document_coverage` (or, for a certificate, `certification_coverage`) entry somewhere in the chunk that keeps it: `normalized`, or `unresolved` for a broken or gated file; a download that links a page (a document folder) is kept by an entry on that page. An `excluded` entry does not keep it: drop the download instead (`product_download_not_in_coverage`, `expected` is the entry to add). The reverse is only a warning (`product_coverage_document_not_in_downloads`). Manufacturer-level certifications are never product downloads.
- The scope parent's page must be one of the record's pages: `official_product_url` (and so `information.product_url`), or, for a record split from a family page with its own product page, an entry in `additional_official_urls` (`product_discovery_product_url_mismatch`, `expected` names the parent page). A page or evidence outside the manufacturer domain is only warned; a coverage page missing from the page inventory is the validation gotchas' `product_coverage_page_not_inventoried` warning.
- Once the partition has a job, validate also predicts the stage checks against that job as warnings, each saying "Staging into this job would fail with ..." and giving the job's value in `expected`.
- A fragment whose own rules can never finalize is refused at upload, before it is stored: a selected parent carrying an excluded or unresolved variant in a `parent_topology` scope, an unselected parent with a selected variant, or a `canonical_identity` that is not the best-ranked alias (`expected` names it).
- A partition's `evidence_refs` must equal exactly the union of its parents' and selected variants' `evidence_refs`. Omit the field and a current server derives that union. If you supply it, neither extras (a datasheet or certificate cited only by the partition) nor omissions are accepted. A current server refuses a wrong set at upload (before the immutable fragment is stored) with an `issues[]` entry whose `expected` is the exact set, when the partition's output and source parents are in the same fragment; with parents in another fragment it can only fail at finalize with `product_discovery_scope_incomplete` and the same `expected`. A scope that failed at finalize stays in `uploading` and cannot be repaired (fragments are immutable): start a new scope. To cite a document in the partition, cite it on the parent or variant first.
- An evidence locator of kind `document_text` needs at least one anchor: `page` (a number), `section` or `paragraph` (text) pointing at the quoted words.
