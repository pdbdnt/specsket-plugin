# Ingestion gotchas: the discovery scope

Read before uploading a discovery-scope fragment. Rules for the chunk are in [ingestion validation gotchas](ingestion-validation-gotchas.md); rules for staging in [ingestion staging gotchas](ingestion-gotchas-staging.md).

## Scope fragment (before upload)

- Every source parent needs `category_occurrences` (send `[]` when you scope by parent product). `checkpoint_ref` is not a key of `execution_partitions`; it belongs to the chunk's `product_presentation.product_structure.checkpoint_ref` (the job's topology checkpoint). A scope upload rejects unknown keys with `Unrecognized key(s)` and a missing one with a bare `Required`; read `issues[].path`.
- Every orderable variant's `canonical_identity` must also appear in its `identity_aliases`. When you omit `orderable_variant_id` (the normal derived flow) a current server adds it for you; on an older server the upload fails with `product_discovery_scope_fragment_invalid` ("Canonical identity must also appear in identity_aliases").
- `product_discovery_evidence_binding_mismatch` names the evidence id and partition. "Not bound to execution partition" means the chunk cites evidence the scope does not bind to that partition; "has no evidence_catalog entry" means the scope predates `chunk_scope_evidence_reuse` (or bound digests only), so include the exact uploaded entry; "not byte-identical" means a repeated entry differs from the uploaded one: omit it (with `chunk_scope_evidence_reuse`) or resend it exactly. This applies to every `evidence_catalog` entry the partition binds, wherever the chunk cites it, not only coverage and readiness; `issues[].path` names the entry and `expected` its uploaded digest. Evidence the scope does not bind to the partition is new evidence: give it a new `evidence_id`.
- `product_discovery_variant_identity_mismatch`: an inspected selector state's `source_identity` is not one of the identities the scope recorded for that record's variants (`issues[].expected` lists the scope's canonical identities still unmatched). Use the uploaded `canonical_identity` or an `identity_aliases` entry; the same code under another manufacturer kind is accepted. A bare `resolved_sku` is checked only when it matches an alias. Two states naming one variant fail with `product_discovery_variant_identity_duplicate`.
- Downloads and coverage name the same files (matched by file URL, ignoring http/https and a leading `www.`). Every `downloads.technical_files` or `downloads.documents` item with a URL needs a `document_coverage` (or, for a certificate, `certification_coverage`) entry somewhere in the chunk that keeps it: `normalized`, or `unresolved` for a broken or gated file; a download that links a page (a document folder) is kept by an entry on that page. An `excluded` entry does not keep it: drop the download instead (`product_download_not_in_coverage`, `expected` is the entry to add). The other way round is only a warning (`product_coverage_document_not_in_downloads`): a normalized document or product certificate file that is neither a download nor a technical drawing, which is fine when it was kept only as a statement. Manufacturer-level certifications are never product downloads.
- The scope parent's page must be one of the record's pages: `official_product_url` (and so `information.product_url`), or, for a record split from a family page with its own product page, an entry in `additional_official_urls` (`product_discovery_product_url_mismatch`, `expected` names the parent page). Such an own page off the manufacturer domain is warned (`product_url_outside_authority_domain`). Chunks saved before these checks are only warned when the server re-validates them (stage-permission renewal, candidate repair). Warnings, never blocking: a coverage page missing from that inventory (`product_coverage_page_not_inventoried`) and web evidence outside the scope's manufacturer domain (`evidence_outside_authority_domain`).
- Once the partition has a job, validate also predicts the stage checks against that job as warnings (for example `product_topology_mismatch`, `integration_source_manifest_conflict`), each saying "Staging into this job would fail with ..." and giving the job's value in `expected`. Fix them before preparing the stage intent.
- A fragment whose own rules can never finalize is refused at upload, before it is stored: a selected parent carrying an excluded or unresolved variant in a `parent_topology` scope, an unselected parent with a selected variant, or a `canonical_identity` that is not the best-ranked alias (`expected` names it).
- A partition's `evidence_refs` must equal exactly the union of its parents' and selected variants' `evidence_refs`. Omit the field and a current server derives that union. If you supply it, neither extras (a datasheet or certificate cited only by the partition) nor omissions are accepted. A current server refuses a wrong set at upload (before the immutable fragment is stored) with an `issues[]` entry whose `expected` is the exact set, when the partition's output and source parents are in the same fragment; with parents in another fragment it can only fail at finalize with `product_discovery_scope_incomplete` and the same `expected`. Older servers return the bare `PRODUCT_DISCOVERY_PARTITION_EVIDENCE_RECONCILIATION_FAILED` at finalize. A scope that failed at finalize stays in `uploading` and cannot be repaired (fragments are immutable): start a new scope. To cite a document in the partition, cite it on the parent or variant first.
- An evidence locator of kind `document_text` needs at least one anchor: `page` (a number), `section` or `paragraph` (text) pointing at the quoted words, e.g. `{ "kind": "document_text", "page": 2 }`. Without one the upload fails with "At least one document anchor is required" and `expected` shows the shape.
