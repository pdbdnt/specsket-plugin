# Dispose a proven empty pre-native chunk refusal

This supported recovery preserves a failed durable original and appends its no-effect disposition. It fails only the exact empty job. It creates no staging permission, successor, native product, media transfer, approval or publication.

## Require both capability and callable action

Use the existing configured connection and call `specsket_get_capabilities`. Require `product_chunk_stage_intent.enabled: true`, `no_effect_disposition_operation: specsket_resolve_product_chunk_preflight_no_effect`, and `no_effect_disposition_scope: known_first_generation_pre_native_refusal`. Require that exact action plus the original and job reads in this chat's actual callable inventory. A running build, plugin installation, capability advertisement or authenticated server tools/list does not establish a desktop callable handle.

If the metadata is absent or disabled, retain existing reads and governed reconciliation. When the server advertises the operation but this chat lacks it, use only the host's supported refresh/restart of the existing MCP entry, preserving its URL and authorization. Report any control limitation. Do not reset OAuth, create another client, change configuration merely to force refresh, switch to hosted ingestion, use a privileged API or guess a missing tool call.

## Read and explain the exact original

Read `specsket_get_product_chunk_stage_intent` and `specsket_get_ingestion_job` under current ownership and authorization. This branch is limited to an unchanged `needs_action` original at `claim_generation: 1`, with an expired claim and exactly one saved result code: `chunk_local_storage_unavailable` or `chunk_local_storage_runtime_commit_mismatch`. An extra result field, another generation, an active claim, generic native rejection, timeout or uncertain transport outcome is ineligible. `next_action: resolve_preflight_no_effect` identifies the proposed branch, not proof that no effect occurred.

Preserve the original operation/job/chunk key, immutable request and validation receipt, request/content digests, actor/client/authorization epoch, execution/partition, job CAS, claim/result and history. The server serializes the original and complete current scaffold, rejects native effects, competing writers and all relevant media/custody history, and rechecks current token, stage authorization and storage identity after waits and effects. Zero counters alone are insufficient. An expired historical staging permission or revoked historical caller is provenance only; this action revives neither. Current stage capability is still mandatory.

Explain that the exact empty job will become failed and a canonical no-effect receipt will be appended, while the terminal original stays unchanged. Follow the existing authorization and write-confirmation rules. Do not enroll a caller, select a runtime, renew permission or redispatch to make this recovery possible.

## Submit one stable disposition request

Call `specsket_resolve_product_chunk_preflight_no_effect` with only:

- `job_id`: the unchanged original job.
- `operation_id`: the unchanged original operation.
- `expected_intent_updated_at`: its exact current original `updated_at`.
- `disposition_idempotency_key`: one stable key of 8–200 characters, separate from the preserved original chunk key.

Do not supply replacement records, receipts, destinations, caller/actor overrides, generations, expiries or successor IDs. A refusal does not authorize rewriting the terminal original or weakening its storage gates.

## Reconcile and reopen

After success, read the same original and job. Require the canonical `no_effect_disposition` with `code: preflight_no_effect_closed`, `phase: resolved`, the exact operation/job/key, original CAS, request/content digests, saved result, original job CAS and resulting failed-job CAS. Preserve the original terminal status and history; report the failed job and no-effect disposition separately from product completion.

A lost, malformed, timed-out or unknown response may have committed. Read the same original's canonical disposition and job before deciding anything else. Under current authorization, the exact same disposition key/CAS may reconcile or replay the canonical receipt even when the job is already failed. Never treat a read error, rejected replay or absent response as proof that no disposition exists. Storage/epoch changes can reject write replay while an authorized canonical original read remains available. Do not blindly redispatch, create a new chunk key/job, revive old authority or claim a definite denial for an unknown outcome.

`next_action: prepare_fresh_execution_or_job` is guidance for a separately reviewed normal workflow, not an automatic successor or new write authorization. Only after canonical disposition and current access/duplicate checks may a fresh supported execution/job be prepared. Retain an explicit evidence link to the original failure and disposition; the API does not allocate or persist a successor relationship. Preserve existing candidates and canonical source identities. Changing only an external record ID does not prove a distinct product; read/reconcile an existing item or use genuinely distinct evidenced input when a new product is intended.

The fresh attempt has its own immutable original/key and current source, validation, scope/execution deadlines, destination, storage admission and confirmation rules. Its success never relabels the historical failed original as successful. An untouched `prepared` generation-zero original instead follows [permission renewal](product-chunk-permission-renewal.md); running or uncertain effects retain their governed reconciliation/custody paths.
