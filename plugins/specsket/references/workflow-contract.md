# Integration workflow contract

Vendor identity, storefront, company-settings evidence and existing-delete custody rules are in [the operator workflow contract](workflow-operator-contract.md); read it for those workflows.

The numbered write sequence below is the default strict workflow for ordinary, Ready, and Deep product imports. The capability-gated [recovery capture contract](product-recovery-capture-contract.md) supplies a separate sequence only for explicitly requested incomplete drafts. Do not silently downgrade an import because recovery is available. Existing strict jobs, signed discovery executions, project-aware products, and non-product workflows never change modes implicitly.

## Visible source review

The browser pass is in [the visible source review](visible-source-review.md): read it before opening a source page. The numbered steps follow.

1. For any MCP-backed workflow, call `specsket_get_capabilities`; stop that live workflow if it is unavailable. Preliminary fast discovery may continue without MCP only when it is clearly labeled and makes no live Specsket claims.
   For Ready or Deep product work, fetch `specsket_get_product_research_contract` once and reuse it while its digest and connected principal remain unchanged. Ready follows its client-analysis route; Deep retains `product@2` server completeness.
   For a question about available Specsket product fields, use the same live research response and follow `field-catalog-contract.md`; the plugin contains presentation rules, not an authoritative field list.
   For verified-designer project-aware discovery, require the advertised project-product capability, explicit project target selection, current Project Intelligence V2 context, and a successful project search-brief validation before public queries. Use only the returned public projection for search. The project sidecar composes around, and never replaces or narrows, the current product field and evidence contracts.
2. Fetch the current entity schema. Use only returned semantic field IDs. Do not pin an old schema version. Read and apply the product-ingestion `ingestion-preview-contract.md`; use `field-catalog-contract.md` for the live human-readable tab and section hierarchy.
3. Fetch current taxonomy versions and resolve taxonomy-backed values with `specsket_search_taxonomy`.
4. For `product@3`, complete client-side linking, dynamic family profiles, exact evidence mapping, and checkpoints before staging; submit profiles once in the request-level catalog and never call server analysis jobs. For legacy `product@2`, retain the server-issued snapshot workflow.
   Before immutable scope finalization, construct every required consumed evidence binding and partition evidence reference under [the evidence contract](evidence-contract.md#immutable-discovery-scope-evidence); on current Specsket derive nothing yourself (see the strict sequence), and keep each exact source and evidence object unchanged afterwards.
   When capabilities advertise product presentation and `product-variant-applicability@1`, use their separate validation, stage, and job-create wrappers automatically without adding either sidecar to the product entity contract. When `product_discovery_scope_contract.enabled` is true, follow the "Strict sequence at a glance" in the product-ingestion skill: upload and finalize the immutable batch scope, create an execution, and bind every ordinary or project-aware validation chunk and job partition to that scope. Ids and digests are server-derived on current Specsket; never compute them, and on an older Specsket without the derivation capability flags stop and tell the user. Use chunk-local `product-source-coverage@2`; the server reconciles selected identities exactly once across all output records, chunks, and sibling jobs before execution completion. When capabilities require `product-readiness@1`, also bind exactly one evidenced parent primary and source-backed grouping/name for every output record through the advertised wrappers. Preserve exact combinations, occurrence accounting, split lineage, and topology metadata across all wrappers; per-record digests are copied from the validation response. For configurable records, reconcile every inspected source state by typed source identity against one enabled presentation combination. Prefer manufacturer SKU/item/article/product/catalogue/order/reference identifiers when explicitly published; otherwise retain the canonical manufacturer-controlled variant URL and use only an explicitly generated internal SKU.
5. For product ingestion, declare `bounded` or `all_discovered` scope and an explicit cap unit. Collection/category defaults mean parent products with every documented in-scope orderable identity; only an explicit exact-identity subset may be sampled and it remains partial. Operational crawl limits never become product caps. Display separate discovered/submitted/output/split-parent, typed identity, documented/submitted combination, excluded, and unresolved counts plus completeness scope. If the source frontier is incomplete, stop for continuation or scope revision. If an unsupported axis or live combination capability requires splitting, preserve every documented combination and show lineage; never truncate or create a Cartesian product.
6. Call `specsket_validate_records` only after the preview and topology gate.
7. If validation reports errors, correct the records and validate again. There is no alternate write path.
8. Show the normalized record count, warnings, and destination review queue to the user. A vendor product job targets that vendor's queue; a designer product job targets only the connected designer's private queue. Obtain separate explicit confirmation immediately before each material write boundary: discovery-scope upload/finalization, execution or job creation, each staging operation, and execution or job completion. A prior confirmation never authorizes a later write phase. Explain and confirm short-lived signed-in review-link creation separately; an account switch always requires its own visible confirmation. When live capabilities advertise `destination_contract_binding: server_default_when_omitted`, a cached callable schema may omit only `destination_plan.destination_contract_version`; the MCP must insert the simultaneously advertised destination version before digest verification and persistence. Do not extend this compatibility rule to the destination plan, routing fields, topology, receipts, digests, or sidecars.
9. Create one or more partition jobs with stable scope-derived idempotency keys, using the validation `job_binding` values. One discovery execution may span several jobs, but every partition is claimed once and binds the same immutable scope digest.
10. Before preparing a new durable original or staging an ordinary unprepared chunk, refresh a receipt with less than 120 seconds remaining. Stage only the exact validated submission with its receipt (the returned digest is optional). Keep chunk indexes and idempotency keys stable across exact retries. A prepared original retains its immutable saved validation receipt; use only the separately advertised and callable [original permission renewal](product-chunk-permission-renewal.md) for an untouched generation-zero original. Expiry never permits replacing that original or replaying an uncertain write.
11. Inspect every `record_results` entry. Correct rejected records using their stable code; do not hide them behind aggregate counts or use another write path.
12. Complete every partition job, then complete the ingestion execution only after all selected identities reconcile exactly once. Always return permanent, non-secret review URLs. Completion only opens human review. When `specsket_get_product_ingestion_execution` is callable, read its `progress` on the original execution ID after a reconnect, before reporting status, and after a completion response. Report selected families, expected outputs, staged outputs, and rejected records separately. Its saved-product, native-verification, certificate, and publication counts are unknown when `null`; never infer them from completed jobs or candidate counts. Use the returned phase, last update, next action, and permanent review URLs, and confirm any native save or publication through its separate authorized readback. If the tool is absent from this chat's callable inventory, state that limitation rather than substituting a privileged API or treating an advertised capability as a callable tool.
   When `product_ingestion_completion_intent.enabled` is true **and all three named tools are callable in this chat**, use `specsket_prepare_product_ingestion_completion_intent` after the separate explicit completion confirmation. Bind a stable operation ID and idempotency key to the exact execution `updated_at` returned by the current read. Preparation must return a durable original-intent receipt before `specsket_dispatch_product_ingestion_completion_intent` is called. After a lost response or reconnect, read `specsket_get_product_ingestion_completion_intent` with that same execution and operation ID, then reconcile or repeat only that original dispatch under current authorization; a changed execution version requires a new review and confirmation. If the capability or any tool is unavailable, retain the existing `specsket_complete_product_ingestion_execution` path and its explicit confirmation requirement. Neither path approves candidates, saves native products, or publishes anything.
   Report private candidate staging, native private saving, product publication and public storefront visibility as separate outcomes. A private save is not publication, and published products alone do not prove public storefront membership or visibility. Keep `null` progress counts unknown and report only the exact native/public readbacks actually performed.
13. Call `specsket_create_review_session` for the completed job. For a product job, pass the accepted candidate the user should see first. Immediately show both the permanent `review_url` and the short-lived signed-in browser link. Ask the host to open `browser_launch_url` in its visible in-app browser when that capability is available. Never claim the browser opened unless the browser action actually succeeded. If browser opening is unavailable or fails, give the user a clearly labeled **Open signed-in Specsket review** link plus the permanent fallback URL. Do not expose, persist, or reuse an expired browser link; create another only after the user asks to open the review again.

For an uncertain product chunk stage, call `specsket_reconcile_product_ingestion_chunk` with the original job, chunk index, idempotency key and immutable digests. For an uncertain storefront review stage, call `specsket_reconcile_vendor_storefront_stage` with the original vendor, key and change-set digest. A committed result identifies the saved native operation. An absent row remains `unknown` while the previous request may still commit; wait and reconcile the same original operation without resubmitting or changing the key. Only authoritative terminal no-commit proof, original-operation custody and quiescence proof, and current access/binding/version checks permit one separately governed same-key, same-digest replay. Receipt expiry, claim expiry, a zero accepted/candidate count or a pre-dispatch denial does not establish that an earlier unknown request stopped or cannot still commit; none permits replay, a new key or a replacement job. If the required proof is unavailable, retain the original operation as `unknown` and stop for governed resolution. Do not automatically replay an uncertain write, substitute a private API, create a replacement key or revive an old authorization. For stale schema, taxonomy, receipt, changed input, authorization, or capability errors, refresh the current contract and repeat the failed read or validation on the same canonical path; do not repeat an uncertain write.
